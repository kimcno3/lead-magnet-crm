# 0022. 개인정보 키 교체

- 상태: 승인
- 날짜: 2026-10-24

## 맥락

개인정보 암호화(ADR 0015)는 키 두 개를 쓴다. `LEAD_ENC_KEY`(이름·전화번호·이메일 AES-256-GCM)와 `LEAD_HMAC_KEY`(같은 폼 중복 판정용 HMAC-SHA256 해시). v0.3.0까지는 키를 바꿀 방법이 없어서, 키를 바꾸면 기동 시 키 확인(`pii_key_check`)이 멈췄다. 키가 샜거나 정기 교체가 필요해도 대응할 수단이 없었다.

두 키는 성격이 다르다.

- **암호화 키**는 읽기만 이전 키로 하면 된다. 이전 키를 들고 있는 동안 행마다 천천히 새 키로 다시 써도 서비스가 멈추지 않는다.
- **HMAC 키**는 중복 판정이 `(form_id, phone_hash)`·`(form_id, email_hash)` 부분 유니크 인덱스와 대상 없는 `ON CONFLICT DO NOTHING`에 걸려 있다(ADR 0007, 0015). 이전 키 해시와 새 키 해시가 섞여 있는 동안에는 같은 연락처의 두 해시가 서로 달라 인덱스가 중복을 놓친다. ROADMAP은 두 해시 컬럼을 함께 두는 기간(expand → contract)을 적어 두었지만, 그러려면 마이그레이션 두 개(새 컬럼·인덱스, 옛 컬럼 삭제)와 그 사이 모든 쓰기·조회의 이중화가 필요하다.

모호한 점과 가정:

- **운영 규모**: 신청 수는 수만 건 이하다(ADR 0020과 같은 가정). 해시 재계산은 행마다 복호화 두 번과 HMAC 네 번이라 수만 건이면 수 초다.
- **중단 허용**: HMAC 키 교체는 드물고(유출 의심 시) 그동안 기동이 몇 초 늦어지는 것은 받아들일 수 있다.
- **키 id 할당**: 운영자가 정한다. 새 키에는 이전에 쓰지 않은 id를 쓴다(같은 id에 다른 키를 두면 그 id로 만든 기존 암호문을 풀 수 없다).

## 결정

**암호문 형식 2(키 id)**
- 새로 쓰는 값은 `2 | keyId(1B) | iv(12B) | ciphertext+tag`, AAD `2:{keyId}:{column}`이다(`common/crypto/PiiCipher`). 키 id까지 AAD에 묶어 키 id 바이트를 바꿔 다른 키로 풀게 할 수 없다(같은 키를 두 id에 둔 경우에도 실패하는 것을 테스트한다).
- 형식 1(`1 | iv | ciphertext+tag`, AAD `1:{column}`, v0.3.0까지)은 키 id 1로 읽는다. 기존 데이터는 그대로 읽히므로 **마이그레이션이 없다**. 형식 1을 새로 쓰지는 않는다.
- `PiiCipher`는 키 링(키 id → 키)을 갖는다. 현재 키로만 쓰고, 읽기는 암호문의 키 id에 맞는 키로 한다. 모르는 키 id는 `PiiCryptoException`("암호문의 키 id에 해당하는 키가 없습니다")이다.

**설정과 기동 실패**
- `LEAD_ENC_KEY`(현재 키), `LEAD_ENC_KEY_ID`(1~255, 기본 1), `LEAD_ENC_PREVIOUS_KEYS`(선택, `id:base64,id:base64`), `LEAD_HMAC_PREVIOUS_KEY`(선택). `app.pii.batch-size`(기본 500)는 재암호화와 HMAC 교체가 함께 쓴다.
- 기동 실패(`PiiCryptoProperties`): 키 id 범위 밖, 이전 키 형식 오류(id 없음, 숫자 아님, 범위 밖, base64 아님, 32바이트 아님, 빈 항목), 이전 키 id 중복, 현재 키 id와 같은 id의 이전 키, 그리고 **한 키 값이 두 자리에 쓰임**(현재·이전 암호화 키와 현재·이전 HMAC 키가 모두 서로 달라야 한다). 메시지에는 환경 변수 이름만 싣고 키 값은 싣지 않는다.
- 키 분리 검사(`SecretKeyMaterial.candidates()`)에 이전 키 두 종류도 넣는다. `JWT_SECRET`과 `FORM_TOKEN_KEY`가 이전 키와 같아도 기동이 실패한다.

**재암호화(온라인, `lead/application/PiiReencryptionService`)**
- 수동 실행 `POST /api/admin/pii/reencrypt[?dryRun=true]` → `{reencrypted, unreadable, remaining, currentKeyId, dryRun, interrupted}`. 스케줄러는 두지 않는다(키 교체는 운영자가 절차로 하는 일이다).
- 현재 키 id가 아닌 암호문이 하나라도 있는 신청을 id keyset으로 `batch-size`건씩 읽어(SQL에서 첫 두 바이트로 키 id를 계산, `get_byte`) 그 암호문만 현재 키로 다시 쓴다. 해시는 그대로다. 배치마다 자기 트랜잭션.
- **잠금**: 배치마다 `pg_try_advisory_xact_lock`(키 `LMREENCR`, 파기 `LMRETAIN`과 다름)을 먼저 잡고, 못 잡으면 이번 실행은 멈추고 `interrupted: true`. 대상 행은 `SELECT ... FOR UPDATE`로 읽고, UPDATE는 `anonymized_at IS NULL`일 때만 한다. 파기가 그 사이에 익명화했으면 원문을 되살리지 않는다.
- **익명화된 행**(암호문 NULL)은 대상이 아니다.
- **풀 수 없는 행**(손상, 모르는 키 id)은 배치를 멈추지 않고 건너뛰어 `unreadable`로 센다. 그 행은 `remaining`에 남고 로그에는 신청 id만 남는다. 한 행 때문에 교체 전체가 막히지 않게 하되, 남은 건수가 0이 되지 않으므로 이전 키를 지워도 된다는 신호가 나오지 않는다.
- **표식 행**: `pii_key_check.enc_check`도 대상이다. 신청이 하나도 남지 않았을 때만 마지막에 현재 키로 바꾼다. 그래서 기동 확인이 현재 키만으로 통과한다면 이전 키로 남은 신청이 없다는 뜻이 된다(이전 키를 너무 일찍 지우면 표식 때문에 기동이 멈춘다, 테스트).
- **남은 건수**: `remaining` = 이전 키로 남은 신청 수 + 표식이 아직 이전 키면 1. **0이면 `LEAD_ENC_PREVIOUS_KEYS`를 지워도 된다.** 드라이런도 같은 값을 준다. 지금 규모에서는 전체 훑기로 센다(키 id 함수 인덱스는 두지 않는다).
- **감사**: 실행마다 `pii.reencrypt` 한 줄(`target_type = lead`, `detail = {count, unreadable, remaining, completed, interrupted[, error]}`, 건수만)을 `recordRequired`로 자기 트랜잭션에 남긴다. 배치가 실패하면 그때까지 커밋한 건수로 `completed: false, error: 예외 클래스 이름`을 **먼저** 기록하고 원래 예외를 올린다(500). 파기(ADR 0020)와 같은 모양이다. 드라이런은 바꾸는 것이 없어 기록하지 않는다(파기 드라이런과 같은 규칙).

**기동 확인(`common/crypto/PiiKeyCheck`)**
- 암호화 키: 표식이 알려진 키(현재 또는 이전) 중 하나로 풀리면 통과. 어느 키로도 안 풀리면 지금처럼 기동 실패. 표식이 이전 키면 "재암호화를 실행하세요" 한 줄을 INFO로 남긴다.
- HMAC 키: 아래 교체.

**HMAC 키 교체(기동 시 오프라인)**
- `LEAD_HMAC_PREVIOUS_KEY`가 설정된 채 기동하고 표식의 `hmac_check`가 이전 키 해시면, `PiiKeyCheck`(`SmartInitializingSingleton`, 웹 서버가 요청을 받기 전) 안에서 `PiiHashRotation` 구현들(`lead/application/LeadHashRotation`)을 부른 뒤 **표식을 마지막에** 새 키 해시로 바꾼다. common은 신청 테이블을 모르고, lead가 common의 포트를 구현한다.
- 행마다 암호문을 풀어 이전 키·새 키 해시를 계산하고, **저장된 해시가 이전 키 해시인 것만** 새 키 해시로 바꾼다. 이미 새 키 해시면 건너뛴다. 어느 쪽과도 맞지 않거나, 해시는 있는데 암호문이 없거나, 암호문을 풀 수 없으면 신청 id를 담은 `PiiKeyRotationException`으로 멈춘다(기동 실패).
- **이어서 끝내기**: 배치마다 커밋하므로 중간에 실패하면 일부 행만 새 키다. 표식은 그대로 이전 키 해시라 다음 기동(이전 키를 그대로 둔 채)이 이전 키 해시인 행만 골라 이어서 바꾼다. 이 상태에서 이전 키를 지우고 기동하면 표식이 이전 키라 "LEAD_HMAC_PREVIOUS_KEY에 이전 키를 두고 기동하세요"로 멈춘다. 섞인 해시로 요청을 받지 않는다.
- **충돌**: 같은 폼에서 새 해시를 이미 다른 신청이 갖고 있으면(이전 키로 서로 다른 해시였던 두 연락처가 새 키로 같아지는 경우. HMAC 충돌이나 직접 수정 외에는 생기지 않는다) 유니크 위반 전에 멈추고 두 신청 id를 알린다(해시·원문은 싣지 않는다). 유니크 위반 예외로 두지 않는 이유는 DB 오류 로그에 해시 값이 실리고, 어느 행인지 운영자가 찾기 어려워서다.
- **여러 인스턴스**: 배치마다 `pg_advisory_xact_lock`(키 `LMREHASH`, 기다림)을 잡는다. 동시에 떠도 한 번에 한 배치만 돌고, 잠금 뒤에 읽으므로 다른 인스턴스가 바꾼 행은 새 키 해시로 보여 건너뛴다. UPDATE는 읽은 해시 그대로일 때만 한다.
- **교체 중 신청**: 기동이 끝나기 전에는 요청을 받지 않으므로 이 인스턴스가 교체 중에 신청을 받지는 않는다. 다만 이전 키로 도는 다른 인스턴스가 남아 있으면 그 인스턴스가 교체 뒤에도 이전 키 해시로 신청을 쓰고, 표식은 이미 새 키라 다음 기동도 그 행을 고치지 않는다. 그래서 절차는 **모든 인스턴스를 내린 뒤** 새 설정으로 띄우는 것이다(GUIDE). 교체 동안 서비스는 멈춘다.
- 교체가 끝나면 이전 키를 지우고 다시 기동한다. 이미 끝났는데 이전 키가 남아 있으면 "LEAD_HMAC_PREVIOUS_KEY를 지우세요" INFO만 남기고 그대로 뜬다.

**로그·메시지**: 키 값, 원문, 해시를 남기지 않는다. 건수와 신청 id만.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 형식 버전 바이트 자체를 키 번호로 쓰기(형식 1 = 키 1, 형식 2 = 키 2) | 바이트 하나 아낌 | 형식과 키가 묶여 형식을 바꿀 때마다 키도 바꿔야 한다. 키 255개 한도가 형식 번호와 겹친다 | 형식과 키 id를 나눈다 |
| 키 id를 별도 컬럼(`*_key_id`)에 저장 | SQL에서 대상 찾기가 쉽고 인덱스를 걸 수 있다 | 마이그레이션, 암호문과 키 id가 어긋날 수 있다(AAD로 묶이지 않음) | 암호문 안에 두고 AAD로 묶는다 |
| 기존 형식 1 데이터를 마이그레이션으로 형식 2로 바꾸기 | 형식이 하나로 정리 | 키가 DB 밖에 있어 SQL로는 할 수 없다 | 형식 1은 키 id 1로 읽고, 키를 바꾸면 재암호화가 형식 2로 바꾼다 |
| 재암호화를 기동 시에 자동 실행 | 운영자 조작 하나 줄음 | 기동이 데이터 크기만큼 늦어진다. 온라인으로 할 수 있는 일이다 | 수동 API로 두고 남은 건수로 끝을 알린다 |
| 풀 수 없는 행이 있으면 재암호화 배치 실패 | fail-closed가 분명 | 손상된 한 행이 교체 전체를 막는다 | 건너뛰고 `unreadable`로 알리며 남은 건수에 남긴다 |
| HMAC 두 해시 컬럼을 함께 두는 기간(expand → contract) | 온라인 교체 | 마이그레이션 두 개, 그 기간 동안 모든 쓰기·중복 판정·파기의 이중화, 인덱스 두 벌 | 드문 작업에 비해 복잡하다. 이 규모에서는 기동 시 몇 초면 끝난다 |
| HMAC 교체를 별도 CLI·잡으로 | 기동과 분리 | 실행 수단이 하나 더 생기고, 그동안 앱이 섞인 해시로 요청을 받지 않게 막는 장치가 따로 필요하다 | 기동 확인 자리에서 하면 "요청 전"이 보장된다 |
| 행마다 어느 키의 해시인지 표시하는 컬럼 | 이어서 하기가 명확 | 마이그레이션 | 이전 키 해시와 같은지로 판단할 수 있다(HMAC은 키 없이 맞출 수 없다) |
| 유니크 위반 예외로 충돌 감지 | 코드가 짧다 | DB 오류 로그에 해시가 실리고 어느 행인지 바로 알기 어렵다 | 바꾸기 전에 같은 폼의 같은 해시를 찾아 두 id를 알린다 |

## 결과

- 쉬워지는 것: 암호화 키는 서비스를 멈추지 않고 바꾼다. 남은 건수로 이전 키를 지워도 되는 시점이 분명하고, 너무 일찍 지우면 기동 확인이 막는다. HMAC 키는 재기동 한 번으로 바뀌고 중간에 실패해도 다시 기동하면 끝난다.
- 어려워지는 것: HMAC 키 교체 동안 기동이 늦어진다(수만 건이면 수 초, 수백만 건이면 분 단위. 그때는 배치 크기와 함께 다시 본다). 이전 키는 교체가 끝날 때까지 시크릿 저장소에 남는다. 키 id는 운영자가 관리해야 한다(쓰지 않은 id).
- 남은 건수는 전체 훑기라 테이블이 커지면 느려진다(키 id 함수 인덱스 검토).
- 다시 볼 조건: KMS·시크릿 매니저(봉투 암호화) 도입 시, 신청 수가 수백만 건이 되어 기동 시 HMAC 교체가 길어질 때, payload 항목을 암호화할 때(재암호화 대상이 늘어난다). 다른 곳이 같은 HMAC 키로 해시를 저장하게 되면(예: 로그인 시도 제한 저장소) 그 도메인도 `PiiHashRotation`을 구현하거나 교체 뒤 버려도 되는 값인지 정한다.
