# 0014. 크리에이터 귀속

- 상태: 승인
- 날짜: 2026-10-23

## 맥락

회사는 크리에이터와 수익 배분(R/S) 방식으로 협업한다. 정산하려면 "어느 크리에이터가 방문자와 신청을 몇 명 데려왔는가"를 캠페인별·채널별로 보여줄 수 있어야 한다. 지금까지 귀속 단위는 채널뿐이었다([ADR 0006](0006-channel-attribution.md)). 한 폼을 여러 크리에이터가 같은 채널(예: 인스타그램)에 동시에 퍼뜨리면 채널만으로는 구분할 수 없다. 방문(`visits`)과 신청(`leads`)은 이미 `link_id`를 기록하고 있다.

## 결정

- **크리에이터**: `creators(id, name, handle, memo, status active|archived, created_by, created_at, updated_at)`를 V3 마이그레이션으로 추가한다. 이름 1~100자, 핸들 100자·메모 2000자 이하(선택, 비우면 NULL), 제어 문자 금지. 수정은 PATCH(없는 필드는 그대로, 핸들·메모의 빈 문자열은 지움), 보관은 `status: "archived"`만 받고 되돌리지 않는다. 다시 보관하면 409 `creator_already_archived`.
- **링크**: `distribution_links.creator_id BIGINT NULL REFERENCES creators`(인덱스). NULL은 크리에이터 없는(운영자 자체) 링크다. 링크는 **폼 × 채널 × 크리에이터(없음 포함)당 하나**이고, ADR 0006처럼 DB 유니크가 아니라 `LinkService`가 막는다(409 `link_exists`). 보관된 크리에이터로는 새 링크를 만들 수 없고(409 `creator_archived`) 이미 만든 링크는 계속 동작한다. 없는 `creatorId`는 404(템플릿 id와 같은 처리). 링크의 크리에이터는 생성 뒤 바꿀 수 없다.
- **귀속 유도**: 방문·신청의 크리에이터는 `link_id → distribution_links.creator_id`로 유도한다. `visits`·`leads` 스키마는 바꾸지 않는다. `/l/{code}`와 `lm` 귀속 흐름(ADR 0006)도 그대로다.
- **지표**: ADR 0005 정의를 그대로 쓰고 묶는 단위만 크리에이터로 바꾼다.
  - `GET /api/admin/campaigns/{id}/stats/creators`: 그 캠페인 폼에 링크가 있는 크리에이터를 등록순으로(데이터가 없어도 0), 마지막에 `creator: null`인 **"직접·자체 링크"** 행(크리에이터 없는 링크 + `direct`)을 항상 둔다.
  - **교집합 규칙 연장**: 전환 방문자는 같은 캠페인·**같은 크리에이터** 안의 교집합이다. 같은 크리에이터라면 방문 채널과 신청 채널이 달라도 전환이다(크리에이터 S의 유튜브 링크로 방문하고 S의 인스타그램 링크로 신청). S 링크로 방문하고 B 링크로 신청한 사람은 S와 B 어느 쪽에서도 전환이 아니다.
  - 각 행의 `channels`는 같은 크리에이터·같은 채널 안의 교집합이다. 크리에이터 행은 링크 채널 네 개, 직접·자체 링크 행은 `direct`까지 다섯 개를 항상 돌려준다.
  - `GET /api/admin/creators/{id}/stats`: 그 크리에이터의 링크가 있는 캠페인만 최신순으로, 그 크리에이터 링크로 귀속된 방문·신청만 센다. 교집합은 캠페인 안에서만 구하므로 캠페인 행끼리 방문자·전환 방문자를 더하지 않는다(합계 행을 두지 않는다).
  - SQL은 `StatsQuery`에 두고 `COALESCE(creator_id, 0)`을 크리에이터 키로 쓴다(0 = 직접·자체 링크, id는 1부터). 캠페인 전체 지표 SQL은 바꾸지 않는다.
- **가정**: 크리에이터 이름과 메모는 사업 파트너 정보이며 신청자 개인정보가 아니다. 운영자 화면과 API에서 원문으로 다룬다. 크리에이터마다 정산 비율 같은 계약 값은 메모로만 둔다(정산 계산은 범위 밖).

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| `visits`·`leads`에 `creator_id` 컬럼 추가 | 집계 SQL이 단순 | 두 큰 테이블 스키마 변경, 링크와 값이 어긋날 수 있다 | 링크가 이미 귀속의 원천이고 link_id로 유도하면 일관성이 저절로 지켜진다 |
| UTM `utm_content`에 크리에이터를 넣고 문자열로 집계 | 스키마 변경 없음 | 이름이 바뀌면 이력이 깨지고 보관 상태를 다룰 수 없다 | 정산 근거로 쓰기에 약하다 |
| 크리에이터 행의 전환을 같은 채널 안에서만 계산 | 채널 행과 숫자가 바로 맞는다 | 같은 크리에이터의 다른 채널로 신청한 사람이 빠진다 | 정산 단위는 크리에이터다. 채널 안 교집합은 `channels`로 따로 준다 |
| 크리에이터 없는 링크와 direct를 따로 행으로 | 더 자세하다 | 정산 대상이 아닌 행이 늘어 읽기 어렵다 | 운영자에게는 "크리에이터 몫이 아닌 것" 한 행이면 충분하다. 채널 펼침에서 direct를 따로 볼 수 있다 |
| (form, channel, creator) DB 유니크 인덱스 | 동시 요청에도 보장 | NULL 처리에 표현식 인덱스가 필요하고 ADR 0006과 규칙 위치가 달라진다 | 운영자 단독 사용이라 ADR 0006과 같은 수준으로 둔다 |

## 결과

- 크리에이터 정산 근거(방문·방문자·신청·전환)를 캠페인 단위와 크리에이터 단위 양쪽에서 같은 정의로 볼 수 있다.
- 크리에이터 행의 합은 캠페인 전체와 다를 수 있다(크리에이터를 넘나든 방문자, ADR 0005의 채널 행과 같은 성질). 행끼리 더하지 않는다.
- 크리에이터 귀속은 링크를 누른 경로에만 의존한다. 크리에이터 링크로 방문한 뒤 직접 주소로 다시 와서 신청하면 신청은 직접·자체 링크로 잡힌다(ADR 0005의 알려진 한계와 같다). 멀티터치가 필요하면 새 ADR로 바꾼다.
- 같은 폼·채널·크리에이터 링크를 동시에 두 번 만들면 둘 다 생길 수 있다(ADR 0006과 같음).

## 변경

### 2026-10-24: 크리에이터 링크의 `utm_content`

- 크리에이터 링크는 생성할 때 `utm_content = creator-{creatorId}`를 저장한다(`DistributionLink.create`, 링크 응답의 `utmContent`). 자체 링크(`creator_id` NULL)는 `utm_content`를 NULL로 둔다. V12가 기존 크리에이터 링크를 같은 값으로 채운다.
- 위 대안표의 "UTM `utm_content`에 크리에이터를 넣고 집계"를 다시 채택한 것이 아니다. 귀속과 집계의 원천은 여전히 링크의 `creator_id`(`link_id`로 유도)이고 `utm_content`는 외부 도구에서 크리에이터를 구분하기 위한 표식일 뿐이다. 크리에이터 이름이 바뀌어도 값은 바뀌지 않는다(id 기반).
- 보관·이름 변경은 `utm_content`에 영향을 주지 않는다.
