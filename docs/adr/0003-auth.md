# 0003. 인증

- 상태: 승인
- 날짜: 2026-10-23

## 맥락

관리자 API(`/api/admin/**`)는 시드로 만든 운영자만 쓸 수 있어야 한다(ADR 0009). 관리자 화면은 SPA이고, 브라우저 입장에서는 admin-web 출처 하나로 API를 부른다(개발은 Vite 프록시, 운영은 nginx). 요구와 제약은 다음과 같다.

- access token은 응답 바디로만 주고 프론트 메모리에만 둔다. localStorage·sessionStorage는 쓰지 않는다.
- refresh token은 HttpOnly 쿠키로 주고, 쓸 때마다 교체하며, 재사용을 감지하면 그 토큰 패밀리 전체를 폐기한다.
- 외부 IdP 없이 단일 앱 안에서 끝나야 하고, `docker compose up` 한 번으로 재현되어야 한다.

## 결정

**access token**
- Spring Security OAuth2 Resource Server의 `NimbusJwtEncoder`/`NimbusJwtDecoder`로 JWT HS256을 쓴다. 키는 `JWT_SECRET` 하나다. UTF-8 32바이트(256비트) 미만이거나 없으면 기동을 실패시킨다(`AuthProperties`).
- 클레임: `iss=lead-magnet-crm`, `aud=lead-magnet-crm-admin`, `sub=운영자 id`, `email`, `iat`, `exp`(15분). 디코더는 서명과 함께 `exp`(필수)·`iss`·`aud`를 검증한다. 시각은 `Clock` 빈에서 얻는다.
- 응답: `{accessToken, tokenType: "Bearer", expiresIn: 900}`.

**refresh token**
- `SecureRandom` 32바이트를 base64url(패딩 없음)로 만든 불투명 토큰이다. 원문은 쿠키로만 보내고 DB(`refresh_tokens.token_hash`)에는 SHA-256 hex만 저장한다. 유효기간 14일.
- 쿠키: `lm_refresh`, `HttpOnly; SameSite=Strict; Path=/api/admin/auth; Max-Age=1209600`. `Secure`는 `COOKIE_SECURE`(로컬 http에서만 false).
- 로그인마다 새 `family_id`를 만든다. refresh는 한 트랜잭션에서 현재 토큰 행을 `SELECT ... FOR UPDATE`로 잠그고 폐기한 뒤 같은 패밀리로 새 토큰을 만든다.
- 이미 폐기된 토큰이 다시 오면 탈취로 보고 그 패밀리의 남은 토큰을 모두 폐기한 뒤 401 `refresh_token_reused`를 준다. 이 폐기는 예외를 던져도 커밋한다. 다른 로그인(다른 패밀리)은 건드리지 않는다.
- 로그아웃은 해당 패밀리를 폐기하고 같은 Path로 `Max-Age=0` 쿠키를 보낸다. 쿠키가 없거나 모르는 토큰이어도 204다.
- 동시에 같은 refresh token으로 두 요청이 오면(탭 두 개 등) 뒤 요청은 재사용으로 판정되어 패밀리가 폐기된다. 보안을 우선해 이 동작을 받아들인다. 프론트는 refresh 요청을 한 번에 하나만 보낸다.

**로그인 실패**
- 없는 이메일과 틀린 비밀번호는 같은 401 `invalid_credentials`로 응답한다. 없는 이메일도 기동 시 만든 더미 BCrypt 해시와 비교해 응답 시간 차이를 줄인다.
- 비밀번호가 UTF-8 72바이트를 넘으면 BCrypt 비교 전에 실패로 처리한다(BCrypt 입력 한계, ADR 0009와 같은 기준).
- 로그에는 마스킹한 이메일과 운영자 id만 남긴다. 비밀번호, refresh token 원문과 해시는 남기지 않는다.

**Security 필터 체인**
- admin 체인(`/api/admin/**`): `login`·`refresh`·`logout`(POST)만 permitAll, 나머지는 Bearer JWT 인증. 세션 STATELESS.
- CORS는 `ADMIN_ORIGIN` 하나만 허용하고 credentials를 허용한다. 메서드 GET/POST/PATCH/DELETE, 헤더 Authorization·Content-Type.
- CSRF 보호는 끈다. 근거:
  - 인증된 관리자 API는 `Authorization: Bearer` 헤더로만 인증한다. 브라우저가 교차 사이트 요청에 자동으로 붙이는 자격 증명이 아니므로 CSRF 대상이 아니다.
  - 쿠키를 쓰는 엔드포인트는 refresh·logout뿐이다. 쿠키가 `SameSite=Strict`라 교차 사이트 요청에는 실리지 않고, `Path=/api/admin/auth`라 다른 API 요청에도 실리지 않는다.
  - refresh 응답(access token)은 CORS로 `ADMIN_ORIGIN`에서만 읽을 수 있다. 공격자가 요청을 보내게 만들어도 결과를 읽을 수 없다.
- 기본 체인(나머지): `/actuator/health`, `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`, `/error`와 공개 경로(`/f/**`, `/l/**`, `/api/public/**`)만 permitAll, 그 밖은 denyAll. 공개 경로는 이슈 #7에서 public 체인으로 분리한다.
- 401·403은 Security 단계에서도 MVC 예외와 같은 ProblemDetail(`code: unauthorized|forbidden`)로 낸다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 서버 세션 + 세션 쿠키 | 구현이 단순하고 즉시 폐기 가능 | CSRF 토큰이 필요하고, 세션 저장소를 두면 확장 시 공유가 필요하다 | 요구사항이 access/refresh 분리와 refresh 교체를 요구한다 |
| access token도 HttpOnly 쿠키 | XSS로 토큰을 읽을 수 없다 | 모든 관리자 API에 CSRF 방어가 필요하다 | refresh 쿠키만 좁은 Path로 두는 편이 공격면이 작다 |
| RS256 비대칭 키 | 검증자에게 공개키만 주면 된다 | 키 쌍 관리가 늘어난다 | 발급자와 검증자가 같은 앱이라 이득이 없다 |
| refresh token도 JWT | DB 조회 없이 검증 | 폐기·재사용 감지에 결국 DB 상태가 필요하다 | 불투명 토큰 + 해시 저장이 더 단순하고 안전하다 |
| 재사용 시 그 토큰만 거부 | 동시 요청에 관대하다 | 탈취된 토큰 계열이 계속 살아남는다 | 보안 불변식(패밀리 전체 폐기)을 따른다 |

## 결과

- access token은 15분 동안 서버에서 폐기할 수 없다. 운영자 비활성화 같은 즉시 차단이 필요해지면 토큰 버전 클레임이나 짧은 TTL을 다시 본다.
- `JWT_SECRET`을 바꾸면 발급된 모든 access token이 무효가 된다(refresh token은 유지되므로 재발급으로 복구된다).
- 폐기·만료된 `refresh_tokens` 행은 쌓인다. 정리 작업은 로드맵으로 미룬다.
- 같은 사이트의 다른 출처(예: public 출처 :8081)에서 보낸 요청에는 `SameSite`만으로는 쿠키가 막히지 않는다. 이 경우에도 refresh 응답은 CORS 때문에 읽을 수 없고, 업로드 HTML은 `allow-same-origin` 없는 sandbox iframe(불투명 출처)에서만 실행한다(ADR 0002). 이 전제가 바뀌면 CSRF 결정을 다시 본다.

## 변경

### 2026-10-23: public 체인 분리와 세션 수명 정리

- "Security 필터 체인"의 "공개 경로는 이슈 #7에서 public 체인으로 분리한다"는 이미 반영되었다. 지금은 체인이 세 개다. admin(`/api/admin/**`, Bearer JWT), public(`/f/**`, `/l/**`, `/api/public/**`, permitAll, 인증 헤더 무시), 기본(헬스·문서 외 denyAll). 포트별 경로 격리는 Security 앞의 `OriginGuardFilter`가 맡는다(ADR 0010).
- 로그아웃은 패밀리를 폐기하므로, 로그아웃한 뒤 같은 refresh token으로 refresh하면 "폐기된 토큰의 재사용"으로 판정되어 401 `refresh_token_reused`가 된다. 이미 패밀리 전체가 폐기된 상태라 추가로 폐기되는 토큰은 없다. 프론트는 이 코드를 `invalid_refresh_token`과 똑같이 "다시 로그인"으로 처리하면 된다.
- refresh 토큰의 14일은 교체할 때마다 새로 시작한다(슬라이딩). 그래서 14일 안에 한 번이라도 refresh하면 세션이 계속 이어지고, 로그인 시점부터의 절대 상한은 없다. 패밀리별 절대 수명(예: 30일)은 로드맵에 둔다.

### 2026-10-23: OpenAPI YAML 경로 허용

- 기본 체인의 permitAll에 `/v3/api-docs.yaml`을 더했다(`/v3/api-docs`와 `/v3/api-docs/**`만으로는 이 경로가 열리지 않아 401이었다). 문서 엔드포인트는 여전히 admin 포트에서만 응답하고 public 포트는 404다(ADR 0010). `docs/api/openapi.yaml`을 이 경로에서 내보낸다.
