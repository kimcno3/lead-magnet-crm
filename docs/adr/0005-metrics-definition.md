# 0005. 지표 정의

- 상태: 승인
- 날짜: 2026-10-23

## 맥락

운영자는 캠페인별, 그리고 채널별로 방문·방문자·신청·전환을 본다. 같은 말("전환")이 사람마다 다르게 읽히면 숫자를 비교할 수 없다. 방문은 `visits`, 신청은 `leads`에 따로 쌓이고(`visits`에는 `campaign_id`가 없어 `forms`를 거친다), 신청에는 방문자 식별자가 없을 수도 있다(쿠키가 없는 제출). 날짜 기준과 채널별 전환의 계산 방식도 정해 두어야 한다.

## 결정

지표는 아래 정의를 그대로 SQL로 옮긴다(`stats/application/StatsQuery`, 지표마다 정의를 주석으로 인용).

| 지표 | 정의 |
|---|---|
| 방문 `visits` | 기간 내 `visits` 행 수 |
| 방문자 `visitors` | 기간 내 `COUNT(DISTINCT visitor_id)` |
| 신청 `leads` | 기간 내 `leads` 행 수 |
| 전환 방문자 `convertedVisitors` | 기간 내 방문 기록이 있는 `visitor_id` 중 기간 내 신청한 `visitor_id` 수(교집합) |
| 전환율 `conversionRate` | `convertedVisitors / visitors`, 소수 넷째 자리 반올림(`0.1234`), `visitors`가 0이면 0 |

- **교집합 규칙**: 전환 방문자는 방문과 신청 양쪽에 같은 `visitor_id`가 기간 안에 있어야 센다. 기간 밖에서 신청한 사람, 방문 기록이 없는 신청은 세지 않는다. 같은 캠페인 안에서만 교집합을 구한다. `visitor_id`가 NULL인 신청은 `leads`에는 들어가지만 `convertedVisitors`에는 절대 들어가지 않는다. 한 방문자가 여러 번 신청해도 전환 방문자는 1이므로 전환율은 1을 넘지 않는다.
- **기간**: `from`, `to`는 `yyyy-MM-dd` 날짜이고 둘 다 선택이다. 없으면 그쪽은 무제한이다. 시각 범위는 `[from 00:00, to 다음날 00:00)`이다. 형식 오류와 `from > to`는 422 `validation_failed`(`errors[].field`가 `from`/`to`), 없는 캠페인은 404.
- **시간대**: 날짜는 `Asia/Seoul` 기준이다. DB는 UTC `timestamptz`로 저장하지만 운영자가 "3월 11일"이라고 말할 때는 한국의 하루를 뜻한다. 그래서 서울 자정을 UTC 시각으로 바꿔 비교한다(`stats/domain/DateRange`). 응답의 `from`/`to`는 요청 값 그대로 돌려주고, 없으면 `null`이다.
- **채널별**: 같은 지표를 채널마다 구한다. 방문과 방문자는 `visits.channel`, 신청은 `leads.channel`로 센다. 채널별 전환은 같은 채널 안의 교집합이다: 그 채널의 방문 기록이 있는 `visitor_id` 중 그 채널로 신청한 수. `instagram, x, youtube, threads, direct` 다섯 채널을 `AttributionChannel` 선언 순서대로 항상 반환하고 데이터가 없으면 0이다.
- **전환율 표현**: JSON 숫자이고 소수 넷째 자리까지 항상 쓴다(`0.6667`, `1.0000`, 0이면 `0.0000`). `BigDecimal`을 `HALF_UP`, scale 4로 계산한다.
- **캠페인 목록**: `created_at` 내림차순, `id` 내림차순이고 데이터가 없는 캠페인도 0으로 포함한다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 전환율 = 신청 / 방문 | 계산이 가장 단순 | 재방문과 중복 제출로 부풀거나 1을 넘는다 | 사람 단위가 아니다 |
| 전환율 = 신청 / 방문자 | 방문자 기준 | 한 사람이 여러 번 신청하거나 `visitor_id`가 없는 신청도 분자에 들어간다 | 분자와 분모가 같은 모집단(방문자)이 아니다 |
| 전환 방문자를 신청의 `COUNT(DISTINCT visitor_id)`로 계산 | 쿼리가 간단 | 방문 기록 없이 신청만 있는 `visitor_id`도 세져 방문자보다 클 수 있다 | 전환율이 1을 넘을 수 있다 |
| 채널별 전환을 캠페인 교집합으로 계산해 채널에 배분 | 한 사람이 한 곳에서만 전환으로 잡힌다 | 채널 행의 합이 맞지 않고 채널별 방문자와 맞지 않는 전환이 나온다 | 각 채널 행이 그 채널만으로 닫혀 읽히는 쪽이 낫다 |
| UTC 날짜 기준 | 구현이 단순, DB 기본값 | 한국 운영자가 보는 하루와 9시간 어긋난다 | 운영자 기준과 맞아야 한다 |
| 사용자 시간대를 파라미터로 받기 | 유연 | 과제 범위를 넘고 API가 복잡해진다 | YAGNI. 필요하면 새 ADR로 바꾼다 |
| 같은 채널 교집합 + 캠페인 전체 교집합(채택) | 채널 행과 캠페인 행 각각이 같은 정의로 닫힌다 | 아래 알려진 한계 | 채택 |

## 결과

- 정의가 SQL에 주석으로 그대로 있어 숫자의 의미를 코드에서 바로 확인할 수 있다.
- 채널 행의 `convertedVisitors` 합과 캠페인 행의 `convertedVisitors`는 다를 수 있다(한 사람이 여러 채널로 방문했거나 방문 채널과 신청 채널이 다를 때). 채널 행끼리 합산하지 않는다.
- **알려진 한계**: 인스타그램 링크로 방문한 사람이 나중에 직접 주소로 다시 들어와 신청하면 신청은 `direct`로 귀속된다(ADR 0006). 이 사람은 캠페인 전체에서는 전환 방문자이지만 채널별로는 `direct`에서만 전환으로 잡힌다(`direct` 방문 기록이 있으므로). `instagram` 행에는 방문자로만 남고 전환으로는 잡히지 않는다. 멀티터치 귀속이 필요해지면 새 ADR로 정의를 바꾼다.
- 시간대를 바꾸거나 여러 시간대를 지원하려면 `DateRange`의 `ZONE`과 이 ADR을 함께 바꾼다.
