# 0018. 게시 시 템플릿 스냅샷과 새 버전 업로드

- 상태: 승인
- 날짜: 2026-10-24

## 맥락

폼은 템플릿 id만 가리켰고 공개 폼은 요청마다 템플릿 원문을 읽었다. 필드 기준(`field_config`)은 생성 시점에 복사했지만(ADR 0013) HTML은 복사하지 않아서, 운영자가 템플릿을 고치면(새 버전 업로드가 생기면) 이미 게시한 공개 폼의 화면과 검증 기준이 어긋난다. 신청 데이터가 쌓이는 중인 폼의 화면이 바뀌면 안 되고, 반대로 아직 게시 전인 draft 폼은 새 버전을 반영할 수 있어야 한다.

## 결정

**게시 시점에 복사한다.** `forms.published_html TEXT`와 `forms.published_template_sha256 CHAR(64)`(V8)를 더한다. `Form.publish(now, html, sha256)`이 상태 전이와 함께 템플릿 원문과 sha256을 폼 행에 복사한다. 공개 API(`/api/public/forms/{slug}`)와 래퍼는 `published_html`만 읽고, 제출 검증은 이미 폼 자신의 `field_config`만 쓴다(`SubmissionValidator`). 따라서 게시 후에는 템플릿 행이 어떻게 바뀌어도 공개 화면과 검증이 그대로다. 마감된 폼도 같다. draft는 두 컬럼이 NULL이고, `ck_forms_published_snapshot` 제약이 draft가 아닌 폼에는 두 값이 있어야 한다고 강제한다.

**새 버전 업로드** `PUT /api/admin/templates/{id}`(multipart `file`, 이름은 바뀌지 않음).
- 검사는 업로드와 같은 `TemplateService.inspect`(확장자·크기·UTF-8·폼 계약·경고, ADR 0017)다. 실패하면 422·413이고 아무것도 바뀌지 않는다(검사는 DB를 바꾸기 전에 끝난다).
- 성공하면 `content`, `sha256`, `fields`, `size`, `inspection`을 바꾸고 `version`을 1 올리며 `updated_at`을 갱신한다.
- 이 템플릿을 쓰는 **draft 폼**은 `field_config`를 새 필드로 다시 스냅샷한다. 이름이 같은 필드는 **운영자가 바꾼 label·required만** 유지한다. 운영자가 바꿨는지는 "폼의 값이 이전 템플릿 값과 다른가"로 판단하므로(별도 override 컬럼을 두지 않는다), 건드리지 않은 값은 새 템플릿을 따른다. type·options는 항상 새 템플릿 값이다. 없어진 필드는 사라지고 새 필드는 추가된다.
- **게시·마감된 폼은 건드리지 않는다.** 응답의 `affectedDraftForms`가 다시 스냅샷한 draft 폼 수다.
- draft가 새 버전 뒤에 게시되면 그때의 새 템플릿이 스냅샷된다.

**동시성: 템플릿 행 → 폼 행 순서로 `PESSIMISTIC_WRITE`를 잡는다.** 게시와 새 버전 업로드가 겹치면, 게시가 옛 템플릿 HTML에 새 필드 기준을, 또는 그 반대를 한 쌍으로 가질 수 있다. 두 경로 모두 `SELECT ... FOR UPDATE`로 (1) 템플릿 행, (2) 폼 행들을 이 순서로 잠근다.
- 새 버전 업로드: 템플릿 잠금 → 템플릿 변경 → draft 폼들 잠금·재스냅샷 → 커밋.
- 게시/폼 수정(`FormService.update`): 폼 엔티티를 읽지 않고 `template_id`만 조회 → 템플릿 잠금 → 폼 잠금 → 읽은 템플릿으로 게시.
- 한 쪽이 커밋하기 전에는 다른 쪽이 기다리고, 커밋된 뒤의 행을 다시 읽으므로 폼의 `published_html`·`published_template_sha256`·`field_config`는 항상 같은 버전에서 온다. 순서가 같아 교착이 없다. 대가로 같은 템플릿을 쓰는 폼의 게시·수정은 서로 직렬화된다(운영자 몇 명 규모에서 문제 없음). 같은 이유로 폼의 필드 수정(PATCH)과 새 버전 업로드도 갱신 유실 없이 한쪽씩 적용된다.
- 낙관적 버전(`@Version`) 대신 비관적 잠금을 쓴 이유: 충돌 시 재시도·409 처리를 만들지 않아도 되고, 충돌 가능성이 낮아 잠금 대기가 거의 생기지 않는다.

**기존 데이터(V8 백필)**: `UPDATE forms SET published_html = t.content, published_template_sha256 = t.sha256 FROM html_templates t WHERE t.id = forms.template_id AND forms.status <> 'draft'`. 기존 게시·마감 폼은 지금 템플릿 내용으로 고정된다. 템플릿에는 `version INTEGER NOT NULL DEFAULT 1`과 `updated_at`(기존 행은 `created_at`)을 더한다. 추가만 하는 변경이다(expand 단계 불필요).

**관리자 화면**
- 템플릿 목록은 버전과 수정일을, 상세는 `v{version}`과 수정 시각을 보인다. 상세의 **새 버전 업로드** 다이얼로그는 성공 시 검사 결과와 새 필드로 다시 만든 draft 폼 수를 보여 주고, 닫으면 상세를 다시 읽는다.
- 폼 패널은 `publishedTemplateSha256`과 `templateSha256`(템플릿의 현재 sha256, 폼 응답에 함께 온다)이 다르면 "게시 시점 템플릿과 현재 템플릿이 다릅니다"를 보인다. 색 없이 기존 `note` 스타일(ADR 0011 흑백 체계)이다.
- 관리자 API CORS에 `PUT`을 허용한다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 템플릿을 불변으로 두고 새 버전은 새 행 | 이력 보존, 스냅샷 컬럼 불필요 | 폼이 가리키는 id를 바꾸는 이동 UI가 필요, 템플릿 목록이 버전마다 늘어남 | 요구는 "같은 템플릿의 새 버전"이고, 폼 쪽 복사 한 번으로 충분하다 |
| 템플릿 버전 이력 테이블 | 이전 버전 열람·되돌리기 | 저장·API·화면 추가 | 필요가 생기면 추가(YAGNI). 게시된 폼은 자기 스냅샷이 이력 역할을 한다 |
| 낙관적 락(`@Version`) | 잠금 대기 없음 | 충돌 시 재시도·409를 모든 호출자가 다뤄야 함, 두 테이블에 걸친 일관성은 여전히 명시 처리 필요 | 비관적 잠금이 더 단순하고 규모에 맞다 |
| 게시 때만 템플릿을 잠금 | 업로드 쪽 단순 | 업로드가 draft 폼의 `field_config`를 쓰는 동안 게시가 낡은 필드를 읽는다 | 양쪽이 같은 순서로 잠가야 한 쌍이 보장된다 |
| draft의 label·required override를 별도 컬럼에 기록 | "운영자 수정"을 정확히 구분 | 컬럼·로직 증가 | 이전 템플릿 값과 비교하면 충분하다. 운영자가 일부러 원래 값과 같게 되돌린 경우는 새 값을 따른다(알려진 한계) |

## 결과

- 게시한 공개 폼의 화면과 검증은 이후 템플릿 변경에 영향받지 않는다. 템플릿을 고치려는 운영자는 새 버전을 올리고, 반영하려면 새 폼을 만들어 게시한다(게시된 폼의 내용 수정은 ADR 0013대로 막혀 있다).
- 폼 응답의 두 sha256이 달라지면 화면이 알려 주므로 "게시 시점과 다른 템플릿"을 눈으로 확인할 수 있다.
- 한계: 운영자가 직접 바꾼 label·required를 일부러 원래 값으로 되돌려 둔 draft는 새 버전에서 새 템플릿 값을 따른다. 게시된 폼에 새 버전을 적용하는 기능은 없다.
- 공개 응답에 쓰는 `published_html`은 템플릿과 같은 크기(최대 512KB)라 폼마다 한 번 더 저장한다.
