# 0006. 채널 귀속

- 상태: 승인
- 날짜: 2026-10-23

## 맥락

운영자는 폼 하나를 instagram, x, youtube, threads에 나눠 배포하고 채널별 방문·신청을 비교하려 한다. 링크 없이 들어온 방문도 있다. 지표는 "방문 = 폼 페이지 로드 1회"로 정의하므로, 링크 클릭과 페이지 로드를 둘 다 방문으로 세면 이중 집계가 된다.

## 결정

- 채널은 링크용 `instagram|x|youtube|threads`(`Channel`)와, 방문·신청에 더해지는 `direct`(링크 없이 들어옴)로 나눈다. 링크 생성 시 `direct`와 모르는 값은 422로 거부한다.
- 폼당 채널별 링크는 하나다. DB에는 (form_id, channel) 유니크를 두지 않고 애플리케이션이 막는다(409 `link_exists`). draft·published 폼에만 만들 수 있고 closed 폼이면 409 `form_closed`.
- 코드는 `SecureRandom`으로 base62(0-9A-Za-z) 8자를 만든다. 유니크 위반(`ux_distribution_links_code`)이면 최대 5회 다시 만들고, 그래도 실패하면 500이다.
- UTM은 생성 시 고정한다: `utm_source=<채널>`, `utm_medium=social`, `utm_campaign=<폼 slug>`. 링크 URL은 `{PUBLIC_BASE_URL}/l/{code}`다.
- **Ruling R1**: `/l/{code}`는 방문을 기록하지 않고 `302 Location: /f/{slug}?lm={code}`로 리다이렉트만 한다(상대 경로). 방문은 `/f/{slug}` 페이지 로드에서 `lm`으로 채널을 정해 한 번만 기록한다(Task 7). 없는 code와 draft 폼은 404, closed 폼은 410이다.
- 귀속 조회는 `LinkService.resolveForForm(formId, code)`가 맡는다. 그 폼의 링크일 때만 링크를 돌려주고, 형식이 틀리거나 없는 코드, 다른 폼의 코드는 비어 있다. 호출자(방문·신청)는 비어 있으면 `direct`로 귀속한다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| `/l/{code}`에서 방문 기록 | 폼 페이지를 거치지 않는 클릭도 센다 | 리다이렉트 후 페이지 로드와 이중 집계 | 방문 정의(페이지 로드 1회)와 어긋난다 |
| (form_id, channel) DB 유니크 | 동시 요청에도 보장 | V1 스키마 수정 또는 새 마이그레이션 필요 | 스키마를 이미 확정했고, 운영자 단독 사용이라 동시 생성 가능성이 낮다 |
| 숫자 id 기반 링크 | 충돌 없음 | 추측 가능, 건수 노출 | 임의 코드가 낫다 |

## 결과

- 방문 집계가 한 곳(폼 페이지 로드)에만 있어 단순하고, 클릭 대비 방문 비율은 이 시스템에서 구할 수 없다.
- 같은 폼·채널 링크를 동시에 두 번 만들면 둘 다 생길 수 있다(드묾). 문제가 되면 유니크 인덱스를 마이그레이션으로 추가한다.
- closed 폼의 `/l/{code}`는 410이라 마감 후 공유된 링크가 조용히 사라지지 않는다.
