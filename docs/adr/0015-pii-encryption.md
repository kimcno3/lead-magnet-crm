# 0015. 개인정보 암호화

- 상태: 승인
- 날짜: 2026-10-23

## 맥락

`leads`에는 신청자 이름·전화번호·이메일이 평문으로 있다(ADR 0008). 이 서비스는 여러 캠페인의 신청자 연락처를 한곳에 모으는 CRM이라, 한 번의 유출로 드러나는 사람이 많다. 관리자 화면 명단도 원문을 그대로 보여 줘서, 화면을 띄워 두거나 캡처하는 것만으로 연락처가 퍼진다.

위협 모델(이번 결정이 막으려는 것):

- **DB 덤프·백업 유출**: 백업 파일, 스냅샷, 잘못 공유한 덤프, 읽기 권한이 있는 DB 계정이 새는 경우. 공격자는 테이블 전체를 갖지만 애플리케이션 환경 변수(키)는 갖지 못한다고 가정한다.
- **어깨너머·화면 공유**: 운영자가 명단을 띄워 둔 화면으로 원문이 보이는 경우.

막지 않는 것(범위 밖):

- 애플리케이션 서버 장악(키와 DB를 함께 얻음), 관리자 계정 탈취(원문 API를 정상적으로 부를 수 있음). 후자는 감사 로그(이슈 #15)로 사후 추적한다.
- `payload` jsonb의 자유 입력 항목. 폼마다 키가 달라 이번에는 암호화하지 않는다.

제약: 중복 신청 판정(ADR 0007)은 같은 폼 안에서 같은 전화번호·이메일을 DB 유니크 인덱스로 막고, 예외 대신 `INSERT ... ON CONFLICT DO NOTHING`을 쓴다(오류 로그에 원문이 실리지 않게). 암호문은 같은 값도 매번 달라서 그대로는 인덱스로 비교할 수 없다. 또 이미 운영 중인 평문 행이 있고, Flyway는 파괴적 변경을 expand → contract로 나눈다.

## 결정

- **암호화**: `name`, `phone`, `email`을 AES-256-GCM으로 암호화해 `name_enc`, `phone_enc`, `email_enc`(BYTEA)에 둔다. 값마다 `SecureRandom` 96비트 IV, 128비트 태그. 저장 형식은 `version(1B) | iv(12B) | ciphertext+tag`이고 현재 버전은 1이다. 버전 1은 컬럼 이름(`name`, `phone`, `email`)을 AES-GCM AAD로 묶는 형식이라, 한 컬럼의 암호문을 다른 컬럼(또는 다른 표식 행)에 옮겨 넣으면 복호화가 실패한다. 변조됐거나 다른 키·다른 컬럼으로 만든 값은 복호화하지 않고 실패시킨다(`PiiCryptoException`, 메시지에 원문·키 없음). JDK `javax.crypto`만 쓴다(`common/crypto/PiiCipher`).
- **중복 판정용 해시**: `phone_hash`, `email_hash`(CHAR(64))에 HMAC-SHA256(`LEAD_HMAC_KEY`, 정규화한 값)의 hex를 둔다. 정규화는 저장 규칙과 같다: 전화번호는 숫자만, 이메일은 앞뒤 공백을 자르고 소문자(`common/crypto/PiiHasher`). 부분 유니크 인덱스 `(form_id, phone_hash) WHERE phone_hash IS NOT NULL`, `(form_id, email_hash) WHERE email_hash IS NOT NULL`을 더한다(`V4__lead_pii_encrypted_columns.sql`). `ON CONFLICT DO NOTHING`은 대상을 지정하지 않으므로 평문 인덱스(V2)와 해시 인덱스를 모두 검사한다. 해시 인덱스만 걸리는 경우도 409가 되는 것을 테스트로 확인했다.
- **키 관리**: 키는 환경 변수 `LEAD_ENC_KEY`, `LEAD_HMAC_KEY`로만 받는다. 둘 다 base64로 인코딩한 32바이트이고 서로 달라야 한다. 없거나 base64가 아니거나 길이가 틀리면 기동을 멈춘다(`PiiCryptoProperties`, 오류 메시지에 키 값을 싣지 않음). `.env.example`의 자리표시 값은 일부러 기동에 실패하는 값이고, README의 `.env` 생성 명령이 `openssl rand -base64 32`로 두 키를 만든다. 키는 DB와 다른 곳(배포 환경의 시크릿 저장소)에 두며 백업도 따로 한다. 키를 잃으면 암호문은 복구할 수 없다.
- **키 일치 확인**: 키를 새로 만들어도 형식만 맞으면 앱이 그대로 떠서, 키가 섞인 데이터가 쌓이고(명단은 복호화 불가, 원문 조회 500) contract 이후에는 같은 연락처의 해시가 달라져 중복 판정이 조용히 깨진다. 이를 막으려고 `pii_key_check` 테이블(V4, `id = 1` 한 행)을 둔다. `PiiKeyCheck`는 기동 중 모든 빈이 만들어진 직후(`SmartInitializingSingleton`, Flyway 마이그레이션이 끝난 뒤), 웹 서버 커넥터가 요청을 받기 전에 돈다. 그래서 틀린 키로 신청이 한 건도 저장되지 않는다. 키가 다르면 컨텍스트 refresh가 실패해 기동이 멈춘다(테스트가 `WebServerInitializedEvent` 전에 실패하는지 확인한다). 백필은 그 뒤 기동 완료 후 러너로 돈다. 행이 없으면 정해진 표식 값을 현재 키로 암호화(AAD `pii_key_check`)·HMAC해 넣고, 있으면 현재 키로 복호화·재계산해 비교한다. 다르면 "LEAD_ENC_KEY가 기존 데이터를 암호화한 키와 다릅니다. 키를 되돌리거나 키 교체 절차(ROADMAP)를 따르세요"(HMAC 키도 같은 형식)로 기동을 멈춘다. 메시지와 로그에는 키 값을 싣지 않는다. 여러 인스턴스가 동시에 처음 떠도 `ON CONFLICT (id) DO NOTHING`으로 한 행만 남고 나머지는 그 행으로 확인한다.
- **읽기**: 명단 API는 복호화한 뒤 가린 값만 돌려준다. 이름은 첫 글자 + `*` + 마지막 글자(두 글자는 첫 글자 + `*`, 한 글자는 `*`), 전화번호는 `010-****-5678`, 이메일은 `h***@example.com`(`common/PiiMasker`). 원문은 새 엔드포인트 `GET /api/admin/leads/{id}/contact` → `{name, phone, email}`로 한 건씩만 준다(`Cache-Control: no-store`). 이 유스케이스(`LeadContactService.reveal`)는 감사 로그(이슈 #15)가 감쌀 자리다. 관리자 화면은 줄마다 "원문 보기"로 그 줄에만 잠시 원문을 보이고 "가리기"나 페이지·필터 이동 시 다시 가린다. 요청마다 토큰을 두어, 화면을 옮겼다가 같은 조건으로 돌아오거나 가리기를 누른 뒤 늦게 온 응답은 버린다.
- **마스킹의 한계**: 가린 값도 일부 정보를 드러낸다. 이메일은 도메인 전체가 보인다(회사 메일이면 소속이 드러난다). 두 글자 이름은 절반(첫 글자)이 보인다. 전화번호는 11자리 중 7자리(앞 3, 끝 4)가 보인다. 운영자가 신청자를 구분하고 같은 사람인지 가늠하는 데 필요한 만큼으로 정했다. 더 가리면 명단에서 사람을 구분하기 어렵고, 원문 보기 호출(=감사 대상)이 늘어난다.
- **손상된 행**: 명단에서 한 행을 복호화하지 못하면(변조, 키 섞임) 명단 전체를 500으로 만들지 않고 그 행만 연락처를 null로 비워 `contactUnavailable: true`로 돌려준다. 로그에는 신청 id만 남기고, 화면은 "복호화 불가"로 표시하며 원문 보기 버튼을 두지 않는다. 원문 조회 API는 그대로 실패한다(500, fail-closed).
- **암·복호화 위치**: `lead/application/ContactProtector` 한 곳에서만 한다. 엔티티와 도메인은 키를 모른다.
- **expand → contract 순서**:
  1. 14a(이 결정, `V4`): 컬럼과 해시 인덱스, 키 확인 테이블을 더한다. V4는 리뷰 중 내용이 바뀌었다(`pii_key_check` 추가). 공유 환경에는 적용된 적이 없지만, 이전 초안 V4를 적용한 로컬 DB는 Flyway 체크섬 불일치로 기동하지 못하므로 `docker compose down -v`로 지우고 다시 띄운다. 새 신청은 평문과 암호문·해시를 **둘 다** 쓴다. 기존 행은 기동 시 `PiiBackfillRunner`가 `id` 순으로 500건씩 채운다(비어 있는 컬럼만 `COALESCE`로 채워 멱등, 배치마다 커밋, 로그에는 건수만). 읽기는 암호문에서 하되, 백필이 끝나기 전의 행만 평문으로 대신한다. 키가 DB 밖에 있어 Flyway SQL로는 백필할 수 없다.
  2. 14b(`V5__drop_lead_plaintext_pii.sql`): 14a가 병합·배포되고 아래 조회가 **0**일 때만 적용한다(평문은 있는데 암호문이 없는 행).
     ```sql
     SELECT count(*) FROM leads
     WHERE (name IS NOT NULL AND name_enc IS NULL)
        OR (phone IS NOT NULL AND (phone_enc IS NULL OR phone_hash IS NULL))
        OR (email IS NOT NULL AND (email_enc IS NULL OR email_hash IS NULL));
     ```
     V5는 같은 조건을 맨 앞의 `DO` 블록으로 검사해 0이 아니면 `RAISE EXCEPTION`으로 마이그레이션을 멈춘다(로그 확인에 기대지 않는다). 평문 유니크 인덱스를 지우고, `ck_leads_contact`를 `phone_enc IS NOT NULL OR email_enc IS NOT NULL`로 바꾸고, 평문 컬럼과 애플리케이션의 평문 쓰기·평문 대체 읽기를 지운다. 이 순서를 지키지 않으면 아직 백필되지 않은 행의 연락처가 사라진다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 암호화 안 함, 화면 마스킹만 | 구현이 가장 단순 | DB 덤프 유출에 무방비 | 위협 모델의 핵심을 막지 못한다 |
| DB 디스크·TDE 암호화 | 애플리케이션 변경 없음 | 정상 DB 계정·덤프로는 평문이 그대로 나온다 | 덤프·백업 유출을 막지 못한다 |
| PostgreSQL `pgcrypto` | SQL로 백필 가능 | 키가 쿼리에 실려 DB 로그·`pg_stat_statements`에 남을 수 있다 | 키가 DB 쪽으로 넘어간다 |
| 결정적 암호화(AES-SIV 등)로 비교 | 컬럼 하나로 비교·복호화 | 같은 값이 같은 암호문이라 빈도가 드러난다. JDK에 없어 라이브러리가 필요 | 비교용 해시와 무작위 IV 암호문을 나누는 편이 단순하고 표준 |
| 중복 판정에 키 없는 SHA-256 | 키 하나 덜 관리 | 한국 휴대전화 번호 공간이 약 10억 개라 덤프만으로 전수 대입해 원문을 되찾을 수 있다(이메일도 사전 대입) | 해시가 사실상 평문과 같다. HMAC은 키 없이는 대입할 수 없다 |
| 같은 키로 암호화와 HMAC | 키 하나 | 한 키가 두 용도에 쓰여 용도 분리 원칙에 어긋난다. 교체 시점도 다르다 | 키를 나눈다 |
| 키 일치 확인 없이 기동 | 단순 | 키를 새로 만들면 섞인 데이터가 조용히 쌓인다 | 기동 시 표식 행으로 확인한다 |
| 손상된 행이 있으면 명단 전체 500 | fail-closed가 분명 | 한 행 때문에 명단 전체를 못 본다 | 명단은 행 단위로 비우고, 원문 API만 fail-closed |
| 한 PR에서 평문 삭제까지 | 빠름 | 배포 중 옛 버전이 평문을 쓰거나, 백필 전 행의 연락처가 사라진다 | expand → contract 규칙 |

## 결과

- 쉬워지는 것: DB 덤프·백업만으로는 연락처를 읽을 수 없다(contract 이후). 명단 기본 화면에서 원문이 보이지 않는다. 원문 열람이 API 한 곳으로 모여 감사 로그를 붙이기 쉽다.
- 어려워지는 것: 연락처로 검색·정렬할 수 없다(정확히 일치하는 검색은 해시로 가능하지만 이번에는 만들지 않는다). 명단 한 페이지마다 복호화 비용이 든다(최대 100건, 무시할 수준). 키를 잃으면 데이터를 잃는다.
- expand 단계 동안은 평문 컬럼이 남아 있어 덤프 유출 방어는 14b 이후에 완성된다.
- 백필 중 같은 폼에 정규화 후 같은 값이 두 행 있으면 해시 인덱스 위반으로 기동이 실패한다. 평문을 저장 시점에 정규화해 왔으므로(ADR 0007) 정상 데이터에서는 일어나지 않는다. 이때 오류에는 해시만 실리고 원문은 실리지 않는다.
- 다시 볼 조건(후속 작업):
  - **키 교체**(ROADMAP "PII 키 교체 절차"): 버전 바이트로 키를 구분하고(버전 → 키 맵), 새 키로 다시 암호화하는 배치를 둔다. HMAC 키 교체는 모든 해시를 다시 계산해야 해서 인덱스를 옮기는 기간 동안 두 해시를 함께 두는 방식이 필요하다. 지금은 키 교체 절차가 없고, `PiiKeyCheck`가 키를 바꾼 채 기동하는 것을 막는다.
  - KMS·시크릿 매니저 연동(봉투 암호화), `payload` 항목 암호화, 보존기한 파기(이슈 #19).
