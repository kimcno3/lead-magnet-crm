# 0007. 중복 신청 정책

- 상태: 승인
- 날짜: 2026-10-23

## 맥락

같은 사람이 폼을 두 번 제출하는 일은 흔하다(더블 클릭, 새로고침 뒤 재제출, 접수 확인 불안). 명단에 같은 사람이 여러 줄이면 신청 수와 연락 대상이 부풀고 지표(신청 수, 전환율)가 왜곡된다. 한편 신청 API는 로그인 없이 열려 있어 응답이 정보를 새게 할 수도 있다. 동시에 두 요청이 들어와도 한 건만 남아야 한다.

## 결정

- 같은 폼에 같은 `phone` 또는 같은 `email`이 이미 있으면 409 `duplicate_submission`으로 거절하고 새 행을 만들지 않는다. 기존 신청은 그대로 둔다.
- 비교는 정규화한 값으로 한다: 전화번호는 숫자만(`010-1234-5678`과 `01012345678`은 같다), 이메일은 소문자. 이름·payload 등 다른 필드는 비교하지 않는다.
- 폼 단위다. 같은 연락처가 다른 폼(다른 캠페인 포함)에 신청하는 것은 중복이 아니다.
- 값이 없는 쪽(NULL)은 비교하지 않는다. 이메일 없이 신청한 두 사람은 중복이 아니다.
- 보장은 DB가 한다 (`V2__lead_dedup_indexes.sql`): 부분 유니크 인덱스 `ux_leads_form_phone (form_id, phone) WHERE phone IS NOT NULL`, `ux_leads_form_email (form_id, email) WHERE email IS NOT NULL`. 애플리케이션은 `INSERT ... ON CONFLICT DO NOTHING`으로 넣고 0행이면 409로 바꾼다. 먼저 조회하고 넣는 방식은 쓰지 않는다(동시 요청에서 둘 다 통과한다).
- 409 응답은 어느 값(전화번호/이메일)이 겹쳤는지, 기존 신청이 무엇인지 알려주지 않는다.
- 예외(유니크 위반)가 아니라 `ON CONFLICT`를 쓰는 이유: PostgreSQL이 위반 오류 로그에 `Key (form_id, phone)=(1, 0101...)`을 싣고 Hibernate가 이를 ERROR로 남겨 개인정보 원문이 로그에 나간다(보안 불변식 위반). `ON CONFLICT`는 오류도, 로그 노이즈도, 사용 불가 트랜잭션도 만들지 않는다. 다만 유니크 충돌만 삼킨다: CHECK·FK 위반은 여전히 오류이고 DB 로그에 행 값이 실릴 수 있으므로, 연락처 필수(`SubmissionValidator`)와 link/channel 일관성(`Attribution`)이 그런 값을 애초에 막는다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| 중복 허용(모두 저장) | 구현이 가장 단순, 정보 손실 없음 | 명단·지표 왜곡, 같은 사람에게 중복 연락 | 명단의 신뢰가 핵심 가치다 |
| 갱신(upsert) | 사용자는 항상 성공을 본다 | 타인의 번호로 기존 신청 내용을 덮어쓸 수 있다(공개 API라 본인 확인이 없다). 최초 시각·귀속 채널이 바뀌어 지표가 흔들린다 | 인증 없는 API에서 기존 데이터를 바꾸게 둘 수 없다 |
| 애플리케이션 조회 후 삽입 | DB 제약 없이 구현 | 동시 요청 경합에서 중복이 생긴다 | DB 보장이 필요하다 |
| 전역(폼 무관) 중복 거절 | 같은 사람이 여러 캠페인에 신청 불가 | 캠페인마다 다시 신청하는 정상 사용을 막는다 | 폼 단위가 업무에 맞다 |
| 거절(409) + DB 부분 유니크 인덱스 | 명단 정합성을 DB가 보장, 공개 API가 기존 데이터를 바꾸지 않음 | 아래 열거 문제 | 채택 |

## 결과

- 쉬워지는 것: 신청 수가 곧 고유 연락처 수라 지표 해석이 단순하다. 동시 제출에도 한 건만 남는다.
- 어려워지는 것 (열거 trade-off): 409로 "이 전화번호/이메일은 이 폼에 이미 신청했다"를 누구나 알아낼 수 있다. 공격자가 번호를 하나씩 넣어 신청자 여부를 확인할 수 있다. 응답을 항상 201로 감추면 막을 수 있지만 정상 사용자가 중복 여부를 알 수 없고 재신청 안내를 못 한다. 폼 신청 여부는 민감도가 낮고 공개 폼은 요청 수 제한이 없는 과제 범위라 사용자 안내를 우선했다. 응답은 어느 값이 겹쳤는지 밝히지 않고, 기존 신청 내용은 돌려주지 않는다.
- 다시 볼 조건: 신청 사실 자체가 민감한 폼(의료 등)을 다루거나 속도 제한을 넣는 단계(v0.2.0)에서는 항상 201로 응답하고 서버에서만 걸러내는 방식을 검토한다.
- 같은 번호를 지운 뒤 다시 받는 기능은 아직 없다(명단 삭제는 범위 밖).
- 이메일 대소문자 정규화는 저장 시점에 한 번 하므로 유니크 인덱스에 `lower()`가 필요 없다. 다른 경로로 행을 넣을 때도 정규화된 값을 써야 한다.

## 변경 기록

- 2026-10-23 (ADR 0015): 연락처를 암호화하면서 같은 규칙을 HMAC 해시 컬럼으로도 보장한다(`V4`: `ux_leads_form_phone_hash`, `ux_leads_form_email_hash`). `ON CONFLICT DO NOTHING`은 대상을 지정하지 않아 평문·해시 인덱스 모두에서 충돌을 거른다. 해시는 숫자만 남긴 전화번호와 앞뒤 공백을 자르고 소문자로 바꾼 이메일로 만든다. contract 단계(V5)에서 평문 인덱스를 지우면 해시 인덱스만 남는다.
