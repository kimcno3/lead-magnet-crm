# 0021. 로그인 시도 제한과 신뢰 프록시 뒤 실제 IP

- 상태: 승인
- 날짜: 2026-10-24

## 맥락

두 가지가 v0.2.0 리뷰에서 높은 우선순위로 남았다(WORKPLAN v0.3.0 후보 1·2).

- **비밀번호 대입**: 로그인은 실패를 감사 로그에 남길 뿐 시도를 막지 않는다(ADR 0003, 0016). ADR 0016 결과 절은 제한을 넣을 때 거절을 한 건씩 기록하지 말고 잠금 시점에 한 번 남기라고 정해 두었다.
- **프록시 뒤 IP**: docker compose에서 관리자 요청은 admin-web nginx를 거쳐 backend admin 포트(:8080)로 간다. 감사 로그 IP는 `getRemoteAddr()`만 쓰므로(ADR 0016) 모든 관리자 요청이 nginx 컨테이너 주소로 남는다. IP별 로그인 제한도 같은 값을 쓰면 모든 운영자가 한 버킷을 나눠 쓰게 된다.

제약과 가정:

- 공개 포트(:8081)는 앞단 프록시 없이 바로 열린다(ADR 0010, compose도 그렇다). 그래서 공개 포트의 `X-Forwarded-For`·`X-Real-IP`는 언제나 클라이언트가 넣은 값이고, 믿으면 제출 rate limit(ADR 0019)을 헤더만 바꿔 우회할 수 있다.
- Tomcat `RemoteIpValve`(`server.tomcat.remoteip.*`, `server.forward-headers-strategy: native`)는 엔진에 붙는 밸브라 **모든 커넥터**에 걸린다. 포트마다 다르게 다룰 수 없다. `ForwardedHeaderFilter`(`framework`)도 포트를 구분하지 않고, 신뢰 프록시 확인이 없다.
- compose default 네트워크 대역은 docker가 그때그때 정한다. 고정하지 않으면 신뢰 대역을 "사설 대역 전체" 같은 넓은 값으로 둘 수밖에 없는데, 리눅스에서는 공개된 포트로 들어온 LAN 클라이언트 주소가 그대로 보이므로(예: `192.168.0.10`) 그 클라이언트의 위조 XFF까지 믿게 된다.
- 서버는 한 대다. 여러 대로 늘리는 것은 ROADMAP이다.

## 결정

### 실제 클라이언트 IP: admin 포트에서만 신뢰 프록시의 XFF를 읽는다

- `common/web/ClientIpFilter`(서블릿 필터, 순서 `HIGHEST_PRECEDENCE`, 모든 필터보다 먼저)가 요청을 감싸 `getRemoteAddr()`·`getRemoteHost()`가 클라이언트 주소를 돌려주게 한다. 그래서 감사 IP(`AuditActors`), 로그인 시도 제한, 제출 rate limit이 모두 같은 값(`getRemoteAddr()`)을 쓴다. 각 사용처는 헤더를 직접 읽지 않는다.
- 규칙(`common/web/TrustedProxies`, Tomcat RemoteIpValve와 같은 방향):
  - **public 포트로 들어온 요청은 아무것도 바꾸지 않는다.** 직전 피어가 신뢰 대역이어도 그렇다(`PublicPort.matches(getLocalPort())`, OriginGuard와 같은 판단).
  - admin 포트에서 직전 피어가 신뢰 프록시가 아니면 그대로 둔다.
  - 직전 피어가 신뢰 프록시면 `X-Forwarded-For`(여러 줄이면 이어 붙임)를 **오른쪽부터** 읽어 신뢰 프록시인 값은 건너뛰고, 신뢰 프록시가 아닌 첫 값을 클라이언트로 쓴다. 그보다 왼쪽 값은 클라이언트가 넣을 수 있으므로 보지 않는다. 모든 값이 신뢰 프록시면 가장 왼쪽 값이다.
  - IP 형식이 아닌 값(호스트 이름, `unknown`, 범위를 넘는 숫자)을 만나면 거기서 멈추고 직전까지 확인한 주소를 쓴다. 호스트 이름을 해석하면 공격자가 정한 이름으로 DNS 조회를 부르게 되므로 하지 않는다.
  - `X-Real-IP`, `Forwarded`(RFC 7239), `X-Forwarded-Proto/Host`는 읽지 않는다. 필요한 것은 IP뿐이다.
- 신뢰 프록시는 `TRUSTED_PROXIES`(`app.trusted-proxies`, 쉼표 구분 IP·CIDR, IPv4·IPv6). 기동 시 검사하고 형식이 틀리거나 호스트 이름이면 기동이 실패한다. 비우면 아무도 신뢰하지 않는다(ADR 0016 이전 동작).
- 기본값은 **admin-web 컨테이너의 고정 주소 하나 `172.16.57.10/32`**다. `docker-compose.yml`이 default 네트워크 대역을 `172.16.57.0/24`로 고정하고(docker 기본 주소 풀 172.17~31.x·192.168.x와 겹치지 않는 값), 자동 할당은 `ip_range: 172.16.57.128/25`로 제한하며, admin-web에 `ipv4_address: 172.16.57.10`을 준다. 대역 전체(`/24`)를 믿지 않는 이유: 게이트웨이 `172.16.57.1`이 들어가는데, Docker Desktop과 리눅스 userland-proxy에서는 공개된 포트로 들어온 연결이 게이트웨이 주소로 보인다. 그러면 호스트 포트(특히 모든 인터페이스에 열린 :8080)에 닿는 누구나(보통 같은 LAN 전체) XFF를 위조해 IP별 로그인 제한을 우회하고 감사 IP를 속일 수 있다. compose 밖(`bootRun`)에서는 이 주소의 피어가 없으므로 사실상 아무도 신뢰하지 않는다.
- **호스트 포트 노출 축소**(같은 이유): compose는 admin 포트와 Postgres 포트를 호스트 루프백에만 연다(`127.0.0.1:${ADMIN_PORT:-8080}:8080`, `127.0.0.1:${POSTGRES_PORT:-5432}:5432`). 관리자 화면은 내부 네트워크로 backend에 닿으므로 영향이 없고, 헬스체크·Swagger·E2E는 호스트의 `localhost`로 쓴다. 공개 포트 :8081과 관리자 화면 :5173은 그대로 모든 인터페이스에 연다.
- **nginx**(`admin-web/nginx.conf`): `X-Forwarded-For $remote_addr`로 덮어쓴다(이전 `$proxy_add_x_forwarded_for`는 브라우저가 보낸 값 뒤에 이어 붙였다). admin-web이 맨 앞단이므로 브라우저 값을 넘길 이유가 없고, 덮어쓰면 위조 값이 아예 backend에 닿지 않는다. 앞에 프록시를 더 두면 이어 붙이기로 되돌리고 그 주소를 `TRUSTED_PROXIES`에 더한다.
- 개발 서버(Vite 프록시)는 XFF를 붙이지 않으므로 루프백 주소가 남는다. 테스트는 루프백을 신뢰 프록시로 둔다(`@IntegrationTest`).

### 로그인 시도 제한

- **실패 수 슬라이딩 윈도**(`common/web/SlidingWindowLimiter`, 인메모리): 창(기본 15분) 안의 실패가 다음 중 하나라도
  - (정규화한 이메일(`Operator.normalizeEmail`, 앞뒤 공백 제거·소문자), 클라이언트 IP) 쌍당 **5회**(`app.auth.login-throttle.email-ip-max-failures`),
  - 이메일당 모든 IP를 합쳐 **50회**(`email-max-failures`, 여러 IP로 나눠 대입할 때만 닿는 상한),
  - 클라이언트 IP(위 규칙의 `getRemoteAddr()`)당 **20회**(`ip-max-failures`, 이메일 무관)

  에 닿으면 다음 시도부터 **429 `too_many_login_attempts`** ProblemDetail과 `Retry-After`(걸린 한도마다 가장 오래된 실패가 창을 벗어날 때까지의 초를 구해 **가장 긴 값**, 1 이상)를 준다. 잠긴 동안에는 **비밀번호를 비교하지 않는다**(올바른 비밀번호도 429). 창 길이 `window`(1분 이상), 키 상한 `max-keys`(기본 10,000).
- 순서: `@Valid`(422) → 세 한도(모두 확인해 가장 긴 대기를 고른다) → 비밀번호 비교(401). 422는 시도로 세지 않는다.
- **브리프와 다른 결정(잠금 키)**: 브리프는 "이메일별 5회/15분"이었으나 **(이메일, IP) 쌍 5회 + 이메일 전체 50회**로 바꿨다. 이메일만으로 잠그면 운영자 이메일을 아는 공격자 한 명이 15분마다 5번 틀려 그 운영자를 계속 로그인하지 못하게 할 수 있다(이메일은 숨기기 어려운 값이다). 쌍으로 잠그면 공격자는 자기 IP에서만 잠기고 운영자는 다른 IP에서 들어온다. 이메일 전체 50회는 여러 IP로 나눠 대입하는 경우의 상한으로 남긴다(이때는 운영자도 막힐 수 있지만 IP를 여럿 쓰는 공격이어야 한다). IP 20회는 그대로다. 리뷰에서 받아들인 변경이다.
- **계정 존재를 드러내지 않는다**: 없는 이메일도 같은 키·같은 한도·같은 429 본문이다. 429는 계정을 조회하기 전에 나가므로 응답 시간도 계정과 무관하다. 한도 안의 시도는 지금처럼 없는 이메일도 더미 BCrypt 해시와 비교한다(ADR 0003).
- **무엇을 실패로 세나**: `invalid_credentials`만. 429 거절은 세지 않는다(거절이 잠금을 늘리지 않는다). 성공하면 그 (이메일, IP) 쌍의 기록을 모두 지우고, 이메일 전체·IP에서는 그 시도의 자리만 돌려준다(운영자의 성공이 분산 대입 기록까지 지우지 않게). 자격 증명과 무관한 실패(DB 오류 등)도 세지 않는다.
- **자리를 먼저 잡는다**: 검사 → 비교 → 실패 기록 순서로 하면 동시에 들어온 요청이 모두 검사를 통과해 한도를 병렬 요청 수만큼 넘긴다. 그래서 검사할 때 자리(시각 한 개)를 미리 기록하고, 성공·중단이면 그 자리를 돌려준다(`LoginThrottle.Attempt.succeeded/failed/abandoned`). 동시 요청이 몇 개든 창 안의 비교 횟수는 한도를 넘지 않는다.
- **기록(ADR 0016 결과 절)**:
  - 잠금이 시작된 실패(그 자리로 창이 꽉 찬 실패) 한 번에 감사 `auth.login.locked` 한 줄: operator 없음, IP 열, detail `email`(가린 값; 닿은 범위가 IP 하나뿐이면 이메일과 무관한 잠금이라 넣지 않는다), `scopes`(`email_ip`·`email`·`ip` 중 닿은 것), `windowMinutes`. 그 실패 자체의 `auth.login.failure`도 지금처럼 남는다. 로그인 기록과 같이 컨트롤러가 트랜잭션 밖에서 `recordBestEffort`로 쓴다.
  - 잠긴 뒤의 거절은 감사 로그에 쓰지 않는다. 애플리케이션 로그에 최대 1분에 한 줄 `로그인 시도 제한 거절: 지난 기록 이후 N건`만 남긴다(`common/web/RejectionTally`, 제출 rate limit과 같은 방식으로 추출). 잠금 시작은 `로그인 시도 제한 시작: 범위=[email_ip], 창=15분` WARN 한 줄이다. 이메일·IP·비밀번호는 로그에 없다.
  - 잠금이 끝난 시점이나 거절 건수를 감사 행에 다시 쓰지 않는다(감사 로그는 쓰기·조회만, ADR 0016).
- **관리자 화면**: 로그인 429면 "잠시 후 다시 시도해 주세요(약 N분)"(N = `Retry-After` 초를 60으로 나눠 올림, 헤더가 없으면 분 없이)를 보여 준다. `ApiError.retryAfterSeconds`로 헤더를 넘긴다. 감사 로그 화면은 "로그인 시도 제한"과 detail 요약(가린 이메일 · 기준 이메일·IP · 15분 창)을 보여 준다.

### 공용 부품

- ADR 0019의 토큰 버킷(`RateLimiter`)은 조금씩 다시 채우는 방식이라 "15분에 5번 틀리면 잠금"과 "가장 오래된 실패가 지나면 풀림"을 표현하지 못하고, 미리 잡은 자리를 돌려주는 기능도 없다. 그래서 알고리즘은 따로 두고, 키 상한 LRU(`BoundedLruMap`)와 거절 건수 로그(`RejectionTally`)는 `common/web`으로 빼서 두 제한이 함께 쓴다. 429에 `Retry-After`를 싣는 예외는 `common/error/TooManyRequestsException`(GlobalExceptionHandler가 헤더를 붙인다)이다.

## 고려한 대안

| 대안 | 장점 | 단점 | 채택하지 않은 이유 |
|---|---|---|---|
| `server.tomcat.remoteip.*`(RemoteIpValve) | 설정만으로 된다, 검증된 구현 | 엔진 밸브라 public 커넥터에도 걸린다. 내부 프록시가 정규식이라 CIDR을 쓰기 어렵다 | 공개 포트에서 XFF를 믿으면 안 된다(제출 rate limit 우회) |
| RemoteIpValve를 상속해 public 포트만 건너뛰기 | Tomcat의 해석 코드를 그대로 쓴다 | 정규식 설정, 커넥터 사정을 밸브에 끼워 넣는다, 단위 테스트가 어렵다 | 필터 하나와 CIDR 매처(`IpAddressMatcher`)로 충분하고 테스트가 쉽다 |
| public 커넥터를 별도 Tomcat `Service`로 분리해 밸브를 나누기 | 포트별 밸브 | Spring Boot가 커넥터 추가만 지원해 서버 구성이 크게 바뀐다 | ADR 0010의 단일 앱 구성을 흔든다 |
| `ForwardedHeaderFilter`(`forward-headers-strategy: framework`) | 표준 필터 | 신뢰 프록시 확인이 없어 누구의 헤더든 믿는다 | 위조 가능 |
| 신뢰 대역을 사설 대역 전체(10/8, 172.16/12, 192.168/16) | 네트워크 고정이 필요 없다 | 공개된 포트로 들어온 LAN 클라이언트의 위조 XFF까지 믿는다 | 대역을 고정하는 편이 좁고 안전하다 |
| nginx는 그대로(`$proxy_add_x_forwarded_for`) 두고 backend가 오른쪽부터 읽기 | 프록시를 겹쳐도 그대로 동작 | 브라우저가 넣은 값이 backend까지 간다 | 맨 앞단이므로 덮어쓰는 편이 단순하다. 오른쪽부터 읽는 규칙은 그대로 두어 겹칠 때도 안전하다 |
| 로그인 제한에 토큰 버킷 재사용 | 코드가 하나 | 3분마다 한 번씩 다시 열려 "잠금"이 되지 않고, Retry-After가 3분으로 나와 사용자에게 혼란 | 슬라이딩 윈도가 요구(15분 5회)와 같다 |
| DB에 실패 기록(`login_attempts` 테이블) | 재시작·여러 대에서도 유지 | 마이그레이션·정리 작업, 실패마다 쓰기(대입 공격이 그대로 DB 쓰기) | 서버 한 대 규모에 과하다. ROADMAP |
| 계정 잠금(운영자가 풀 때까지) | 대입을 확실히 막는다 | 누구나 운영자 이메일로 틀려 계정을 잠글 수 있다(서비스 거부) | 시간이 지나면 풀리는 창이 낫다 |
| 거절마다 감사 로그 한 행 | 추적이 쉽다 | 공격이 감사 테이블 쓰기 폭주가 된다 | ADR 0016 결과 절. 잠금 시작 한 줄 + 로그 건수 요약 |
| 이메일만으로 잠금(브리프 원안) | 단순, 분산 대입에도 같은 한도 | 이메일을 아는 공격자 한 명이 운영자를 계속 막는다 | (이메일, IP) 쌍 + 높은 이메일 전체 상한으로 바꿨다 |
| 신뢰 대역을 compose 네트워크 전체(`/24`) | admin-web 주소를 고정하지 않아도 된다 | 게이트웨이(.1)로 들어오는 호스트 포트 연결의 위조 XFF까지 믿는다 | admin-web 고정 주소 `/32`만 믿는다 |
| 성공해도 IP 기록 유지 | 구현이 단순 | 운영자가 많이 로그인하는 사무실 IP가 실패 없이 잠긴다 | 실패만 센다 |

## 결과

- 쉬워지는 것: 한 IP에서 이메일 하나에 15분 5회, IP당 15분 20회, 이메일 하나에 모든 IP 합쳐 15분 50회로 대입 속도가 묶인다. 공격자가 운영자 이메일로 틀려도 운영자는 다른 IP에서 로그인할 수 있다. 감사 로그와 제한이 nginx 뒤에서도 실제 브라우저 주소를 쓴다. 공개 포트에서 헤더를 위조해 제출 rate limit을 우회할 수 없다는 것을 테스트로 고정했다.
- 어려워지는 것: compose 네트워크 대역과 admin-web 주소를 고정했다. 기존 네트워크가 다른 대역이거나 고정 전에 만든 것이면 `docker compose down` 뒤 다시 올려야 한다(네트워크를 다시 만든다). 대역이 이 컴퓨터의 다른 네트워크·VPN과 겹치면 대역·admin-web 주소·`TRUSTED_PROXIES`를 함께 바꿔야 한다. admin 포트와 Postgres는 다른 컴퓨터에서 직접 닿지 않는다(필요하면 포트 매핑을 바꾸되, 그때도 `TRUSTED_PROXIES`를 넓히지 않는다). 새 환경 변수 `TRUSTED_PROXIES`.
- 알려진 한계:
  - 인메모리·인스턴스별이다. 재시작하면 기록이 지워지고(급할 때 잠금을 푸는 방법이기도 하다), 여러 대면 한도가 대수만큼 커진다.
  - 키 상한(10,000)을 넘게 이메일·IP를 바꿔 가며 보내면 가장 오래 안 쓴 키부터 잊는다. IP를 대량으로 바꾸는 분산 대입은 이메일 한도만 막는다.
  - 운영자와 같은 IP(같은 NAT 뒤)에 있는 공격자, 또는 IP를 10개 넘게 쓰는 공격자(이메일 전체 50회)는 여전히 운영자를 창 단위로 막을 수 있다. 계정을 영구히 잠그지는 않는다.
  - 같은 공인 IP 뒤의 여러 운영자는 IP 한도(실패 20회)를 나눠 쓴다.
  - 호스트에서 루프백 :8080으로 직접 보낸 요청은 게이트웨이 주소로 들어오고 신뢰하지 않으므로 XFF를 무시한다(감사 IP는 게이트웨이 주소). admin-web 컨테이너 안에서 보낸 요청만 XFF를 믿는다. 운영 배포에서는 admin 포트를 프록시 뒤에만 열고 그 프록시 주소만 `TRUSTED_PROXIES`에 넣는다.
  - 잠금 직전에 다른 동시 시도가 성공·중단되어 자리를 돌려주면 `auth.login.locked`가 실제로는 꽉 차지 않은 창에서 남을 수 있다(드물고, 기록이 한 줄 더 남는 쪽이다).
- 다시 볼 조건: 서버 여러 대(공유 저장소), 공개 포트 앞에 CDN·프록시 두기(그때는 공개 포트도 신뢰 프록시 규칙이 필요하다), 2단계 인증.

## 변경 기록

- 2026-10-24 (v0.3.0 최종 리뷰): 운영자가 알아야 할 한계 두 가지를 분명히 적는다. 동작은 바뀌지 않는다.
  - **여러 IP로 퍼뜨린 공격에 의한 밀어내기**: 인메모리 저장소는 키를 10,000개(`max-keys`)까지만 들고 가장 오래 안 쓴 키부터 버린다. 공격자가 이메일·IP를 바꿔 가며 키를 10,000개 넘게 만들면 (이메일, IP) 쌍과 IP 카운터가 밀려나 기록이 사라질 수 있다. 이때도 이메일 하나에 모든 IP 합쳐 15분 50회라는 이메일 전체 상한은 그 이메일의 카운터가 밀려나지 않는 한 유지되지만, 쌍·IP 한도는 보장하지 못한다. 분산 대입에 대한 근본 대응은 공유 저장소로 옮기는 것이며 [ROADMAP](../ROADMAP.md)에 있다.
  - **`TRUSTED_PROXIES` 오설정**: 값이 실제 앞단 프록시 주소와 다르면 backend는 XFF를 믿지 않고 `getRemoteAddr()`(프록시 주소)를 클라이언트 IP로 쓴다. 그러면 모든 로그인이 한 IP로 보여 IP 한도(15분 20회 실패)를 모든 운영자가 나눠 쓰고, 실패가 20번 쌓이면 모든 사용자가 잠긴다. 감사 로그의 IP도 모두 프록시 주소로 남는다. 다른 프록시나 로드 밸런서 뒤에 둘 때는 그 hop의 주소로 `TRUSTED_PROXIES`를 바꾸고, 감사 로그의 IP가 실제 브라우저 주소인지 확인한다.
