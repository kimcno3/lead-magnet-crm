## Global Constraints

### 보안 불변식 (CLAUDE.md 원문 그대로 적용)
- :8080 admin 출처는 `/api/admin/**`와 관리자 화면만, :8081 public 출처는 `/f/**`, `/l/**`, `/api/public/**`만 제공한다. OriginGuardFilter가 맞지 않는 포트로 들어온 요청을 404로 차단한다. 관리자 API의 CORS는 admin 출처만 허용한다.
- 업로드 HTML은 `<iframe sandbox="allow-scripts allow-forms" srcdoc>`로만 렌더링한다. `allow-same-origin` 금지. 제출은 postMessage로 래퍼에 넘기고 래퍼가 검증한 뒤 public API로 POST한다. 공개 응답에는 CSP를 붙인다.
- access token은 응답 바디로만 준다. refresh token은 HttpOnly, SameSite=Strict, Path=/api/admin/auth 쿠키로 주고, 사용할 때마다 교체하며 재사용을 감지하면 토큰 패밀리 전체를 폐기한다.
- 개인정보(전화번호, 이메일)는 로그에 원문으로 남기지 않는다(`common/PiiMasker` 사용). 시크릿은 커밋하지 않고 새 환경 변수는 `.env.example`과 `docker-compose.yml`에 추가한다.
- 보안 관련 변경에는 실패 케이스 테스트를 함께 넣는다.

### 아키텍처 (DDD 레이어링)
- 루트 패키지 `com.leadmagnet.crm`. 도메인 패키지: `auth, template, campaign, form, link, tracking, lead, stats, common`.
- 각 도메인 패키지는 하위 패키지로 나눈다.
  - `domain`: 엔티티(애그리거트 루트), 값 객체, 도메인 예외, Spring Data 리포지토리 인터페이스. 상태 전이·불변식은 엔티티 메서드 안에 둔다(예: `form.publish()`). setter 금지, 생성은 정적 팩토리나 생성자.
  - `application`: 유스케이스 서비스(`@Transactional`), 커맨드·결과 record.
  - `api`: 컨트롤러와 요청·응답 DTO(record). 컨트롤러는 리포지토리를 직접 쓰지 않는다. 엔티티를 응답으로 직접 내보내지 않는다.
  - `config`(필요 시): 보안·웹 설정, 필터.
- 다른 애그리거트는 id로 참조한다(JPA 연관관계 대신 `Long campaignId`). 다른 도메인 데이터가 필요하면 그 도메인의 application 서비스나 리포지토리를 읽기 용도로 쓴다.
- CRUD는 JPA, 지표 집계는 네이티브 SQL(`JdbcTemplate`/`NamedParameterJdbcTemplate`). 스키마 변경은 Flyway(`V{n}__*.sql`)로만, PR당 최대 하나. 이미 있는 `V1__init_schema.sql`은 수정하지 않는다.
- jsonb 컬럼은 Hibernate 6 `@JdbcTypeCode(SqlTypes.JSON)`으로 매핑한다.

### 에러 응답
- 모든 에러는 `ProblemDetail`(RFC 9457, `application/problem+json`). `common/error`에 `ErrorCode` enum(HTTP 상태 + 기계용 코드 문자열)과 `DomainException`(ErrorCode 보유), `GlobalExceptionHandler`(`@RestControllerAdvice`)를 둔다. ProblemDetail에는 `type`(`https://leadmagnet.example/problems/{code}`), `title`, `status`, `detail`, 확장 속성 `code`를 넣는다. 검증 실패(422)는 `errors: [{field, message}]`를 붙인다.
- 사용하는 상태: 400(요청 형식 오류), 401, 403, 404, 409, 410, 413, 422.
- 인증 실패(401)·인가 실패(403)도 Spring Security entry point/access denied handler에서 같은 ProblemDetail 형식으로 낸다.

### API 문서
- springdoc-openapi(`org.springdoc:springdoc-openapi-starter-webmvc-ui:2.8.17`). 컨트롤러에 `@Tag`, `@Operation`, 주요 응답 코드 `@ApiResponse`를 단다. `/v3/api-docs`, `/swagger-ui/**`는 admin 포트에서만 제공한다.

### 테스트
- 통합 테스트는 `@IntegrationTest`(Testcontainers `postgres:17-alpine`, 컨텍스트 공유) + RestAssured. 각 테스트 전에 `DatabaseCleaner.truncateAll(jdbc)`. 새 테이블을 만들면 `DatabaseCleaner`에 추가한다.
- 도메인 규칙은 Spring 없이 순수 JUnit 단위 테스트로 먼저 쓴다.
- 테스트 메서드 이름은 한국어 `행위_조건_결과` 형식(기존 테스트와 같게).
- 모든 기능은 성공 케이스와 실패 케이스를 함께 테스트한다.
- 실행: `cd backend && JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew build` (Gradle 툴체인이 JDK 21로 컴파일·테스트한다. Docker가 떠 있어야 한다). 커밋 전에 전체 빌드가 통과해야 한다. 테스트 출력에 경고·스택트레이스 소음이 없어야 한다.

## Task 3: 인증 (이슈 #3)

브랜치 `feat/3-auth`. ADR 0003 인증.

### 정리
- 기존 `auth` 패키지 클래스를 레이어로 옮긴다: `Operator`, `OperatorRepository` → `auth.domain`; `OperatorSeeder`, `OperatorSeedProperties` → `auth.application`; `PasswordConfig` → `auth.config`. 기존 테스트도 같은 패키지로 옮기고 계속 통과해야 한다.
- `common/error`(ErrorCode, DomainException, GlobalExceptionHandler)를 이 Task에서 만든다. 이후 Task가 모두 이것을 쓴다.
- springdoc 의존성을 추가한다.

### 토큰
- access token: JWT HS256, Spring Security `NimbusJwtEncoder`/`NimbusJwtDecoder`(키 = `JWT_SECRET`, 32바이트 미만이면 기동 실패). 클레임: `iss=lead-magnet-crm`, `aud=lead-magnet-crm-admin`, `sub=<operatorId>`, `email`, `iat`, `exp`(발급 후 15분). 디코더는 iss·aud·exp를 검증한다.
- refresh token: `SecureRandom` 32바이트 → base64url(패딩 없음) 원문은 쿠키로만 보낸다. DB `refresh_tokens.token_hash`에는 SHA-256 hex만 저장. 유효기간 14일. 로그인마다 새 `family_id`(UUID).
- 쿠키 이름 `lm_refresh`, 속성 `HttpOnly; SameSite=Strict; Path=/api/admin/auth; Max-Age=1209600`, `Secure`는 `COOKIE_SECURE`.
- 시간은 테스트에서 고정할 수 있게 `java.time.Clock` 빈을 주입해 쓴다.

### 엔드포인트 (admin 포트)
| 메서드·경로 | 요청 | 성공 | 실패 |
|---|---|---|---|
| `POST /api/admin/auth/login` | `{email, password}` | 200 `{accessToken, tokenType:"Bearer", expiresIn:900}` + refresh 쿠키 | 422 형식 오류, 401 `invalid_credentials`(없는 이메일과 틀린 비밀번호를 구분하지 않는다. 없는 이메일도 더미 해시로 비밀번호 비교를 수행해 응답 시간 차이를 줄인다) |
| `POST /api/admin/auth/refresh` | 쿠키 | 200 새 access token + 교체된 refresh 쿠키 | 401: 쿠키 없음·모르는 토큰·만료·폐기된 토큰. 폐기된 토큰이 다시 오면(재사용) 그 패밀리의 모든 토큰을 폐기하고 401 `refresh_token_reused` |
| `POST /api/admin/auth/logout` | 쿠키 | 204, 해당 패밀리 폐기, 쿠키 삭제(`Max-Age=0`, 같은 Path) | 쿠키가 없어도 204 |
| `GET /api/admin/auth/me` | Bearer | 200 `{id, email}` | 401 |

- refresh 교체는 같은 트랜잭션 안에서 현재 토큰 행을 `SELECT ... FOR UPDATE`(JPA `@Lock(PESSIMISTIC_WRITE)`)로 잠그고 `revoked_at`을 채운 뒤 같은 family로 새 토큰을 만든다.
- 도메인: `RefreshToken` 엔티티에 `isExpired(now)`, `isRevoked()`, `revoke(now)`. 재사용 판단은 application 서비스(`TokenService` 또는 `AuthService`)에서 한다.

### Security 설정
- SecurityFilterChain을 둘 둔다.
  - admin 체인: `securityMatcher("/api/admin/**")`. `/api/admin/auth/login|refresh|logout`은 permitAll, 나머지 authenticated. `oauth2ResourceServer().jwt()`. 세션 STATELESS. CSRF 비활성화(Bearer 헤더 인증이며, 쿠키를 쓰는 refresh·logout은 SameSite=Strict와 Path로 보호한다는 근거를 ADR에 적는다). CORS: `ADMIN_ORIGIN` 하나만 허용, credentials 허용, 메서드 GET/POST/PATCH/DELETE, 헤더 Authorization·Content-Type.
  - 기본 체인: 나머지 전부. `/actuator/health`, `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`은 permitAll. 공개 경로(`/f/**`, `/l/**`, `/api/public/**`)는 이 Task에서는 permitAll로 둔다(Task 7에서 공개 체인으로 분리). 그 밖은 denyAll.
  - 401/403은 ProblemDetail JSON.

### 테스트 (필수 목록)
- 성공: 로그인 → access token으로 `/me` 200, 응답 바디에 accessToken, `Set-Cookie`에 `HttpOnly`, `SameSite=Strict`, `Path=/api/admin/auth`가 있다.
- 성공: refresh가 새 access token과 다른 refresh 쿠키를 준다. 새 refresh 토큰으로 다시 refresh할 수 있다.
- 성공: logout 후 그 refresh 토큰으로 refresh하면 401.
- 실패: 틀린 비밀번호 401, 없는 이메일 401(두 응답의 바디 code가 같다), 형식이 틀린 요청 422.
- 실패: 토큰 없이 `/me` 401(ProblemDetail), 서명이 다른 토큰 401, 만료된 토큰 401(Clock을 조정하거나 과거 exp로 서명한 토큰), aud가 다른 토큰 401.
- 실패: refresh 재사용 — 토큰 A로 refresh해서 B를 받은 뒤 A를 다시 쓰면 401 `refresh_token_reused`, 그 뒤 B도 401.
- 실패: 만료된 refresh 토큰 401.
- 실패: 응답·로그 어디에도 refresh 토큰 원문 해시나 비밀번호가 남지 않는다(OutputCapture로 비밀번호 미포함 확인).
- 실패: `JWT_SECRET`이 32바이트 미만이면 컨텍스트 기동 실패(단위 테스트로 설정 검증 로직 확인 가능).
- CORS: `Origin: http://localhost:5173` 프리플라이트는 허용, `Origin: http://evil.example`은 거부(403).

## Task 4: HTML 템플릿 업로드 (이슈 #4)

브랜치 `feat/4-template-upload`. ADR 0004 HTML 폼 계약. 의존성 `org.jsoup:jsoup:1.23.2`.

### 폼 계약 (ADR 0004에 그대로 기록)
- 파일은 단일 `.html` 또는 `.htm`, UTF-8 텍스트, 비어 있지 않음, 512KB(524288바이트) 이하(`app.template.max-bytes`). multipart 한도(`spring.servlet.multipart.max-file-size`)는 1MB로 두고, 그 사이 크기는 애플리케이션이 413으로 막는다. multipart 한도를 넘으면 `MaxUploadSizeExceededException`도 413 ProblemDetail로 변환한다.
- 문서에 `<form>`이 정확히 하나 있어야 한다.
- 필드 = form 안의 `input`, `select`, `textarea` 중 `name` 속성이 있는 것. `input type`이 `submit|button|reset|image`면 필드가 아니다. `type=file`, `type=password`가 있으면 거부한다.
- 필드 이름 규칙 `^[a-zA-Z][a-zA-Z0-9_]{0,49}$`, 최대 50개. 같은 이름은 `radio`/`checkbox`일 때만 허용(하나의 필드로 묶고 `options`에 value를 모은다).
- 예약 필드: `name`(이름), `phone`(전화번호), `email`(이메일). `phone` 또는 `email` 중 하나는 반드시 있어야 한다(ADR 0008 `ck_leads_contact`와 일치).
- 추출 결과 `fields`(jsonb): `[{name, type, required, label, options}]`. `type`은 `text|email|tel|number|date|textarea|select|radio|checkbox|hidden|url` 중 하나로 정규화(그 밖의 input type은 `text`). `required`는 `required` 속성. `label`은 `<label for=id>` 텍스트 → 감싼 `<label>` 텍스트 → `placeholder` → `name` 순서. `options`는 select의 option value 또는 radio/checkbox value 목록(없으면 빈 배열).
- 스크립트·스타일·외부 리소스는 막지 않는다(샌드박스가 격리한다, ADR 0002). `action` 속성은 무시된다(래퍼가 제출을 가로챈다).

### 엔드포인트 (admin, 인증 필요)
| 메서드·경로 | 성공 | 실패 |
|---|---|---|
| `POST /api/admin/templates` multipart `file`(필수), `name`(선택, 없으면 파일명에서 확장자 제거, 최대 100자) | 201 `{id, name, size, sha256, fields, createdAt}` + `Location` | 401, 413 크기 초과, 422 빈 파일·확장자·UTF-8 아님·form 없음/여러 개·금지 필드·필드 규칙 위반·연락처 필드 없음(각각 다른 `code`) |
| `GET /api/admin/templates` | 200 `[{id, name, size, fieldCount, createdAt}]` 최신순 | 401 |
| `GET /api/admin/templates/{id}` | 200 `{id, name, size, sha256, fields, content, createdAt}` | 401, 404 |

- 도메인: `HtmlTemplate` 엔티티(생성 시 sha256 계산), 필드 추출기 `FormContractParser`(Jsoup, 순수 클래스, 단위 테스트 대상)와 값 객체 `FormField`.

### 테스트
- 단위(`FormContractParser`): 정상 폼 필드·라벨·옵션·required 추출, radio 묶기, form 0개/2개, file·password 거부, 이름 규칙 위반, 51개 필드, 연락처 필드 없음.
- 통합: 업로드 성공 201과 목록·상세 조회, 미인증 401, 빈 파일 422, `.txt` 422, 600KB 413, 2MB 413, 없는 id 404.

## Task 5: 캠페인과 폼 (이슈 #5)

브랜치 `feat/5-campaign-form`. ADR 0013 캠페인·폼 상태 모델(새 번호, README 표에 추가).

### 도메인 규칙
- `Campaign`: `name`(1~100자), `description`(선택, 2000자 이하), `startsAt`/`endsAt`(선택, 둘 다 있으면 starts < ends), `status` `active|archived`. `archive()`는 active → archived, 다시 archive하면 409. archived 캠페인에는 폼을 만들 수 없다(409).
- `Form`: `campaignId`, `templateId`, `slug`, `title`(1~200자), `consentText`(1~2000자, 필수), `fieldConfig`(생성 시 템플릿 `fields`를 복사한 스냅샷), `status` `draft|published|closed`.
  - 전이: `publish()` draft → published(`publishedAt`), `close()` published → closed(`closedAt`). 그 밖의 전이는 409 `invalid_form_transition`.
  - 내용 수정(title, consentText, fieldConfig의 label·required)은 draft에서만. 그 밖에는 409 `form_not_editable`.
  - fieldConfig 수정은 기존 필드의 `label`, `required`만 바꿀 수 있다. 필드 추가·삭제·이름 변경은 422.
- `Slug` 값 객체: `^[a-z0-9][a-z0-9-]{1,62}[a-z0-9]$`. 생략하면 소문자+숫자 8자 랜덤 생성. 중복이면 409 `slug_taken`.

### 엔드포인트 (admin, 인증 필요)
| 메서드·경로 | 성공 | 실패 |
|---|---|---|
| `POST /api/admin/campaigns` `{name, description?, startsAt?, endsAt?}` | 201 캠페인 | 422 |
| `GET /api/admin/campaigns` | 200 `[{id, name, status, startsAt, endsAt, formCount, createdAt}]` 최신순 | |
| `GET /api/admin/campaigns/{id}` | 200 캠페인 + `forms: [{id, slug, title, status, publishedAt, closedAt}]` | 404 |
| `PATCH /api/admin/campaigns/{id}` `{name?, description?, startsAt?, endsAt?, status?("archived")}` | 200 | 404, 409, 422 |
| `POST /api/admin/campaigns/{id}/forms` `{templateId, title, consentText, slug?}` | 201 폼(draft) | 404 캠페인·템플릿, 409 archived·slug 중복, 422 |
| `GET /api/admin/forms/{id}` | 200 `{id, campaignId, templateId, slug, title, consentText, fieldConfig, status, publishedAt, closedAt, createdAt}` | 404 |
| `PATCH /api/admin/forms/{id}` `{title?, consentText?, fieldConfig?, status?("published"|"closed")}` | 200 | 404, 409, 422 |

### 테스트
- 단위: Campaign·Form 상태 전이 성공과 잘못된 전이, 수정 가능 여부, Slug 규칙.

## Task 6: 배포 링크 (이슈 #6)

브랜치 `feat/6-links`. ADR 0006 채널 귀속.

### 규칙
- 채널 enum `Channel`: `instagram|x|youtube|threads`(링크용), 방문·신청 귀속에는 `direct`가 더해진 `AttributionChannel`(또는 같은 enum에 direct를 두고 링크 생성 시 direct를 거부).
- 폼당 채널별 링크는 하나(애플리케이션 규칙. 이미 있으면 409 `link_exists`). draft·published 폼에만 만들 수 있고 closed 폼이면 409.
- `code`: base62 8자 `SecureRandom`, 충돌 시 재시도(최대 5회).
- UTM: `utm_source=<channel>`, `utm_medium=social`, `utm_campaign=<form slug>`.
- URL: `{PUBLIC_BASE_URL}/l/{code}`.

### 엔드포인트
| 메서드·경로 | 성공 | 실패 |
|---|---|---|
| `POST /api/admin/forms/{id}/links` `{channel}` | 201 `{id, channel, code, url, utmSource, utmMedium, utmCampaign, createdAt}` | 401, 404, 409, 422(direct·모르는 채널) |
| `GET /api/admin/forms/{id}/links` | 200 목록(채널 순서 instagram, x, youtube, threads) | 401, 404 |
| `GET /l/{code}` (공개) | 302 `Location: /f/{slug}?lm={code}` | 404 없는 code 또는 draft 폼, 410 closed 폼 |

- 귀속 결정(Ruling, PLAN 4절 보완): `/l/{code}`는 방문을 기록하지 않고 리다이렉트만 한다. 방문은 `/f/{slug}` 페이지 로드에서 한 번만 기록하며 `lm` 값으로 채널을 정한다(Task 7). PLAN의 "방문 = 페이지 로드 1회"를 지키고 이중 집계를 막기 위해서다. ADR 0006에 기록한다.
- 공개 응답의 404·410은 이 Task에서는 ProblemDetail로 둔다(Task 7에서 공개 경로 처리 방식을 정리).

### 테스트
- 단위: code 생성 형식, 채널 파싱.
- 통합: 4개 채널 링크 생성과 URL·UTM, 같은 채널 두 번 409, closed 폼 409, direct 422, 미인증 401, `/l/{code}` 302와 Location, 없는 code 404, draft 폼 404, closed 폼 410.

## Task 7: 공개 출처 격리와 방문 추적 (이슈 #7)

브랜치 `feat/7-public-isolation`. ADR 0002 HTML 격리, ADR 0010 단일 앱·포트 분리. 보안 핵심 Task.

### 포트와 필터
- `PUBLIC_PORT`(기본 8081)로 Tomcat 커넥터를 하나 더 붙인다(`WebServerFactoryCustomizer<TomcatServletWebServerFactory>`). 테스트는 `app.ports.public-port=0`으로 랜덤 포트를 쓰고, 실제 포트는 커넥터에서 읽어 노출하는 빈(예: `PublicPort`)으로 얻는다.
- `OriginGuardFilter`(가장 앞쪽 서블릿 필터, Security 필터보다 먼저): `request.getLocalPort()`가 public 커넥터 포트면 `/f/**`, `/l/**`, `/api/public/**`만 통과, 나머지 404(ProblemDetail). admin 포트면 `/f/**`, `/l/**`, `/api/public/**`를 404. admin 포트에서 허용되는 것은 `/api/admin/**`, `/actuator/health`, `/v3/api-docs/**`, `/swagger-ui/**`, `/swagger-ui.html`, 그 밖은 지금처럼 Security가 처리.
- 공개 SecurityFilterChain: `securityMatcher("/f/**", "/l/**", "/api/public/**")`, permitAll, STATELESS, CSRF 비활성화, CORS 없음(공개 API는 같은 출처 래퍼만 호출), 인증 헤더가 와도 무시(Resource Server 미설정).
- 공개 응답 보안 헤더(공개 경로 전부, 필터로):
  - `Content-Security-Policy: default-src 'none'; script-src 'self' 'unsafe-inline'; style-src 'self' 'unsafe-inline' https:; img-src 'self' data: https:; font-src 'self' data: https:; connect-src 'self'; frame-src 'self'; form-action 'none'; base-uri 'none'; frame-ancestors 'none'`
  - `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`.
  - 근거(ADR 0002): srcdoc 문서는 부모의 CSP를 상속하므로 업로드 HTML의 인라인 스크립트·스타일을 허용하려면 `'unsafe-inline'`이 필요하다. 래퍼 페이지에는 신뢰할 수 없는 내용이 서버에서 섞이지 않는다(모든 동적 값은 JS `textContent`/`srcdoc` 속성으로만 넣는다). `connect-src 'self'`와 `form-action 'none'`으로 외부 전송을 막는다.

### 공개 엔드포인트
| 메서드·경로 | 동작 |
|---|---|
| `GET /f/{slug}` | published 폼이면 200 `text/html` 래퍼 셸. 방문 1건 기록. draft 404, closed 410(간단한 HTML 안내 페이지), 없는 slug 404 |
| `GET /f/_assets/form-wrapper.js` | 래퍼 스크립트(정적 리소스, `src/main/resources/static/f/_assets/` 또는 컨트롤러). slug 규칙상 `_`로 시작할 수 없어 충돌하지 않는다 |
| `GET /api/public/forms/{slug}` | published면 200 `{slug, title, consentText, fields, html}`(fields = fieldConfig, html = 템플릿 원문). draft 404, closed 410 |

### 래퍼 셸과 스크립트 (vanilla JS, React와 분리)
- 셸 HTML(서버 템플릿 엔진 없이 정적 문자열): 제목 영역, `<iframe sandbox="allow-scripts allow-forms" title="신청 폼">`(srcdoc은 JS가 채움), 동의 체크박스 영역(래퍼가 그림), 제출 결과 영역, `<script src="/f/_assets/form-wrapper.js" defer>`. 셸 자체에 슬러그 외 동적 값이 없다(슬러그는 `location.pathname`에서 읽는다).
- 스크립트:
  1. `/api/public/forms/{slug}`를 가져와 제목·동의 문구를 `textContent`로 넣는다.
  2. 템플릿 html의 `</body>` 앞(없으면 끝)에 브리지 스크립트를 넣어 `iframe.srcdoc`에 설정한다. 브리지는 form `submit`을 `preventDefault`하고 `FormData`를 `{name: value | value[]}`로 모아 `parent.postMessage({type: "lm:submit", fields}, "*")`.
  3. `message` 이벤트에서 `event.source === iframe.contentWindow`이고 `event.origin === "null"`이며 `data.type === "lm:submit"`인 것만 받는다. 필드 이름이 fieldConfig에 있는지, 필수 값이 있는지 클라이언트 검증 후, 래퍼의 동의 체크박스가 체크되어 있어야 `POST /api/public/forms/{slug}/submissions`로 보낸다(`{fields, consent: true, lm}`; `lm`은 현재 URL의 쿼리). 결과를 래퍼 영역에 표시하고 iframe에 `{type: "lm:result", ok}`를 postMessage로 돌려준다.
- 제출 API 자체는 Task 8. 이 Task에서는 래퍼가 호출할 경로만 정해 둔다.

### 방문 추적
- 방문자 쿠키 `lm_vid`(UUID v4, `HttpOnly; SameSite=Lax; Path=/; Max-Age=31536000`, Secure는 `COOKIE_SECURE`). `/f/{slug}`와 `/l/{code}`에서 없으면 발급한다. 형식이 틀린 값은 새로 발급.
- `GET /f/{slug}` 200일 때 `visits` 1행: `form_id`, `visitor_id`, `referrer`(최대 512자), `user_agent`(최대 512자), 채널은 `lm` 쿼리가 이 폼의 링크 code면 그 링크·채널, 아니면 `direct`.
- `tracking` 패키지: `Visit` 엔티티, `VisitRecorder` 서비스.

### 테스트 (격리 검증은 실패 케이스 중심)
- public 포트로 `/api/admin/auth/login`, `/api/admin/auth/me`, `/actuator/health`, `/v3/api-docs` 요청 → 404.
- admin 포트로 `/f/{slug}`, `/l/{code}`, `/api/public/forms/{slug}` → 404.
- public 포트의 `/f/{slug}` 응답에 CSP(위 문자열 그대로), nosniff, X-Frame-Options DENY가 있다. 응답 HTML에 `sandbox="allow-scripts allow-forms"`가 있고 `allow-same-origin`이 없다.
- `Origin: http://localhost:8081`(public 출처)에서 admin API로 CORS 프리플라이트 → 거부.
- public 포트 응답에는 `lm_refresh` 쿠키가 절대 없다.
- 방문: lm 없음 → direct 1행, 올바른 lm → 해당 채널, 다른 폼의 code나 모르는 code → direct. 같은 쿠키로 두 번 → visits 2행·visitor_id 1개. 쿠키 없으면 `Set-Cookie: lm_vid` 발급(HttpOnly, SameSite=Lax).
- draft 404, closed 410, 없는 slug 404, `/api/public/forms/{slug}` 200 바디에 fields와 html.
- 래퍼 스크립트는 Node 없이 검증하기 어렵다. 이 Task에서는 정적 파일이 public 포트로 200, `application/javascript` 또는 `text/javascript`로 서빙되는지 테스트하고, 브라우저 동작은 이후 Playwright E2E로 검증한다.

## Task 8: 신청 접수와 명단 (이슈 #8)

브랜치 `feat/8-leads`. ADR 0007 중복 신청 정책. 마이그레이션 `V2__lead_dedup_indexes.sql`.

### 제출 `POST /api/public/forms/{slug}/submissions` (public 포트)
- 요청: `{fields: {<name>: string | string[]}, consent: boolean, lm?: string}`, `Content-Type: application/json`만 허용(그 밖은 415가 아니라 400으로 처리해도 된다).
- 폼 상태: draft·없음 404, closed 410.
- 검증(fieldConfig 기준, 실패 시 422 + `errors[]`):
  - fieldConfig에 없는 필드 → 422 `unknown_field`.
  - required 누락·빈 문자열 → `required`.
  - 값 길이 1000자 이하, checkbox 외에는 배열 불가.
  - `email` 타입 또는 `email` 필드: 간단한 형식 검사, 소문자 정규화.
  - `tel` 타입 또는 `phone` 필드: 숫자만 남겨 `^01[016789]\d{7,8}$`(한국 휴대전화). 저장은 숫자만.
  - select·radio·checkbox: options에 있는 값만.
  - `consent`가 true가 아니면 422 `consent_required`.
  - phone·email이 모두 비어 있으면 422 `contact_required`.
- 저장: `name`·`phone`·`email` 필드는 컬럼으로, 나머지 필드는 `payload`. `campaign_id`는 폼에서, `visitor_id`는 `lm_vid` 쿠키(없거나 형식 오류면 null), `consent_at`=now. 채널은 `lm`이 이 폼의 링크 code면 그 채널, 아니면 direct.
- 중복(ADR 0007): 같은 폼에 같은 phone, 또는 같은 email이 이미 있으면 409 `duplicate_submission`. 경합에도 안전하도록 V2에서 부분 유니크 인덱스 `(form_id, phone) WHERE phone IS NOT NULL`, `(form_id, email) WHERE email IS NOT NULL`을 만들고, 유니크 위반을 409로 변환한다.
- 성공 201 `{status: "received"}`(신청 id 등 내부 정보는 돌려주지 않는다).
- 로그에는 PiiMasker로 가린 값만.

### 명단 `GET /api/admin/campaigns/{id}/leads` (admin, 인증)
- 쿼리: `page`(0부터, 기본 0), `size`(기본 20, 최대 100), `formId?`, `channel?`.
- 200 `{items: [{id, formId, formTitle, channel, name, phone, email, payload, createdAt}], page, size, totalElements, totalPages}` 최신순.

## Task 9: 성과 지표 (이슈 #9)

브랜치 `feat/9-stats`. ADR 0005 지표 정의.

### 정의 (네이티브 SQL에 그대로 보이게)
- 기간: `from`, `to`는 `yyyy-MM-dd`(둘 다 선택), `Asia/Seoul` 기준 날짜. `from` 00:00 이상, `to` 다음날 00:00 미만. `from > to`면 422.
- 방문 `visits` = 기간 내 visits 행 수.
- 방문자 `visitors` = 기간 내 `COUNT(DISTINCT visitor_id)`.
- 신청 `leads` = 기간 내 leads 행 수.
- 전환 방문자 `convertedVisitors` = 기간 내 방문 기록이 있는 visitor_id 중 기간 내 신청한 visitor_id 수(교집합).
- 전환율 `conversionRate` = convertedVisitors / visitors, 소수 넷째 자리 반올림(`0.1234`), visitors가 0이면 0.
- 채널별: 같은 지표를 `channel`별로(방문은 visits.channel, 신청은 leads.channel, 전환은 같은 채널 안의 교집합). 다섯 채널(`instagram, x, youtube, threads, direct`)을 항상 0 포함해 반환.

### 엔드포인트 (admin, 인증)
| 경로 | 응답 |
|---|---|
| `GET /api/admin/campaigns/{id}/stats?from&to` | `{campaignId, from, to, visits, visitors, leads, convertedVisitors, conversionRate}` |
| `GET /api/admin/campaigns/{id}/stats/channels?from&to` | `{campaignId, from, to, channels: [{channel, visits, visitors, leads, convertedVisitors, conversionRate}]}` |
| `GET /api/admin/stats/campaigns?from&to` | `{from, to, campaigns: [{campaignId, name, status, visits, visitors, leads, convertedVisitors, conversionRate}]}` 최신 캠페인순 |

- 404 없는 캠페인, 401, 422 날짜 형식·범위.
- `stats` 패키지는 엔티티 없이 `StatsQuery`(NamedParameterJdbcTemplate) + `StatsService` + 컨트롤러.

### 테스트
- 통합: 시드한 visits·leads로 숫자를 정확히 검증(방문 5, 방문자 3, 신청 2, 전환 방문자 2, 전환율 0.6667 같은 손계산 값), 채널별 0 포함, 기간 경계(Asia/Seoul 자정 전후), 방문 없음 → 전환율 0, 다른 캠페인 데이터가 섞이지 않음, 미인증 401, 없는 캠페인 404, from>to 422.
