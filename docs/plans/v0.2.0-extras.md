## Global Constraints

- v0.1.0 계획의 Global Constraints(보안 불변식, DDD 레이어링, ProblemDetail 계약 + `errors[].code`, 테스트 규칙, 커밋 규칙)를 그대로 따른다: `.superpowers/sdd/v0.1.0-backend/global-constraints.md`. 단 CSP는 ADR 0002 변경 기록이 최신이다.
- Flyway: 이미 적용된 파일 수정 금지, PR당 마이그레이션 최대 하나, 파괴적 변경은 expand → contract로 PR을 나눈다.

- 브라우저 E2E(`e2e/`)가 깨지지 않게 한다. UI 문구·구조를 바꾸면 E2E도 함께 고친다(E2E 실행은 컨트롤러가 한다).

## Task 13: 크리에이터별 성과 추적 (이슈 #13)

브랜치 `feat/13-creators`. ADR 0014 크리에이터 귀속. 마이그레이션 `V3__creators.sql`.

- `creators(id, name VARCHAR(100), handle VARCHAR(100) NULL, memo TEXT NULL, status active|archived, created_by, created_at, updated_at)`; `distribution_links.creator_id BIGINT NULL REFERENCES creators`, 인덱스.
- 규칙: 링크는 폼 × 채널 × 크리에이터(없음 포함)당 하나(애플리케이션 규칙, ADR 0006 연장). 보관된 크리에이터로는 새 링크를 만들 수 없다(409). 방문·신청의 크리에이터는 link를 통해 유도한다(visits·leads 스키마 변경 없음).
- API(admin): `POST/GET /api/admin/creators`, `GET/PATCH /api/admin/creators/{id}`(이름·핸들·메모·status archived); `POST /api/admin/forms/{id}/links`에 `creatorId?` 추가, 링크 응답에 `creator {id, name}`; `GET /api/admin/campaigns/{id}/stats/creators?from&to` → 크리에이터별(크리에이터 없는 링크와 direct는 "직접·자체 링크" 한 행으로) 방문·방문자·신청·전환·전환율, 같은 크리에이터 안의 교집합(ADR 0005 규칙 연장). `GET /api/admin/creators/{id}/stats?from&to` → 그 크리에이터의 캠페인별 지표.
- UI: 사이드바 "크리에이터" 메뉴(목록·생성·수정·보관), 폼 링크 영역에서 크리에이터를 골라 링크 생성(채널 × 크리에이터 표), 캠페인 성과 탭에 "크리에이터별" 표.
- 테스트: 크리에이터 CRUD, 링크 중복 규칙(같은 폼·채널·크리에이터 409, 다른 크리에이터는 허용), 보관 크리에이터 409, 크리에이터별 지표 손계산(크리에이터 2명 + 자체 링크 + direct), 캠페인 간·크리에이터 간 교집합 격리, 미인증 401.

## Task 14: 개인정보 암호화와 마스킹 (이슈 #14)

두 PR로 나눈다(expand → contract).

### 14a (`feat/14-pii-encryption-expand`, `V4__lead_pii_encrypted_columns.sql`)
- `leads`에 `name_enc BYTEA, phone_enc BYTEA, email_enc BYTEA, phone_hash CHAR(64), email_hash CHAR(64)` 추가. 부분 유니크 인덱스 `(form_id, phone_hash) WHERE phone_hash IS NOT NULL`, `(form_id, email_hash) ...`.
- 암호화: AES-256-GCM(랜덤 96비트 IV, 저장 형식 `version(1B)|iv(12B)|ciphertext+tag`), 키 `LEAD_ENC_KEY`(base64 32바이트, 없거나 길이 틀리면 기동 실패). 해시: HMAC-SHA256(`LEAD_HMAC_KEY`, 정규화된 값) hex. `common/crypto`의 `PiiCipher`, `PiiHasher`(순수 클래스, 단위 테스트).
- 쓰기: 새 신청은 평문 컬럼과 암호·해시 컬럼을 **둘 다** 쓴다(expand). 중복 판정은 해시 인덱스로(`ON CONFLICT DO NOTHING` 유지).
- 기존 행 백필: 애플리케이션 시작 시 `PiiBackfillRunner`가 `*_enc IS NULL AND (phone IS NOT NULL OR email IS NOT NULL OR name IS NOT NULL)`인 행을 배치로 채운다(멱등, 로그에는 개수만).
- 읽기: 명단 API는 암호 컬럼을 복호화해 **마스킹**해서 반환(`홍*동`, `010-****-5678`, `h***@example.com`). 원문은 새 엔드포인트 `GET /api/admin/leads/{id}/contact` → `{name, phone, email}`(이 호출은 Task 15 감사 로그 대상).
- UI: 명단은 마스킹 표시, 행의 "원문 보기" 버튼 → contact API 호출 결과를 그 행에만 잠시 표시.
- 테스트: 암·복호화 왕복, 변조된 암호문 거부, 키 누락·길이 오류 기동 실패, HMAC 결정성, 백필 멱등, 중복 판정이 해시로 동작(대소문자 다른 이메일), 마스킹 형식, contact API 인증, 로그에 원문 없음.
- ADR 0015 개인정보 암호화.

### 14b (`feat/14-pii-encryption-contract`, `V5__drop_lead_plaintext_pii.sql`)
- 평문 `name, phone, email` 컬럼과 기존 평문 유니크 인덱스, `ck_leads_contact`를 `phone_enc`·`email_enc` 기준 CHECK로 교체하고 평문 컬럼 삭제. 애플리케이션의 평문 쓰기 제거. 14a가 병합·배포된 뒤에만 적용(ADR 0015에 순서 기록).

## Task 17: 게시 시 템플릿 스냅샷 (이슈 #17)

브랜치 `feat/17-publish-snapshot`. 마이그레이션 `V8__form_published_snapshot.sql`(forms.published_html TEXT, forms.published_template_sha256 CHAR(64)). ADR 0018.
- 템플릿 새 버전 업로드: `PUT /api/admin/templates/{id}`(multipart file) → 계약 검사·필드 재추출, sha256 갱신. 이미 이 템플릿을 쓰는 draft 폼은 다음 게시 때 새 내용을 쓴다(draft 폼의 fieldConfig는 새 필드로 다시 스냅샷하되 운영자가 바꾼 label·required는 이름이 같으면 유지).

- 테스트: 게시 후 템플릿 교체 시 공개 폼 html·검증 불변, draft 폼은 새 내용, 계약 위반 새 버전 422, 백필.

## Task 18: 데이터 품질 방어 (이슈 #18)

브랜치 `feat/18-data-quality`. 마이그레이션 `V9__visit_bot_flag.sql`(visits.is_bot BOOLEAN NOT NULL DEFAULT false). ADR 0019.
- 봇 방문: User-Agent가 봇 패턴(googlebot, bingbot, facebookexternalhit, twitterbot, slackbot, kakaotalk-scrap, headless, curl, python-requests 등, 목록은 설정)이면 `is_bot=true`로 기록하고 지표에서 제외(지표 SQL에 `NOT is_bot`, ADR 0005 변경 기록). 링크 미리보기 크롤러가 방문을 부풀리지 않게.
- Honeypot: 래퍼가 제출 JSON에 항상 빈 `hp` 필드를 보낸다. `hp`가 비어 있지 않으면 201을 주되 저장하지 않는다(봇에게 차단 사실을 알리지 않음, 로그에는 카운트만).
- 최소 작성 시간: `GET /api/public/forms/{slug}` 응답에 서버 서명 토큰 `ft`(HMAC, 발급 시각+slug)를 주고 래퍼가 제출에 포함. 발급 후 2초 미만 제출이나 서명 불일치·24시간 초과는 422 `invalid_form_token`(사람에게는 "다시 시도" 안내).
- Rate limit: 제출 API에 IP당 분당 10회, 방문자 쿠키당 분당 5회(인메모리 토큰 버킷, 설정 가능) → 429 `too_many_requests`(ProblemDetail, Retry-After). 프록시 뒤 IP는 신뢰 설정(`server.forward-headers-strategy`)과 함께 ADR에 기록.
- 테스트: 봇 UA 방문 is_bot·지표 제외, honeypot 무저장 201, 토큰 위조·빠른 제출·만료, rate limit 429와 Retry-After, 정상 흐름 영향 없음(E2E 포함: E2E는 사람 속도라 통과해야 함).

## Task 19: 보존기한 파기와 동의 문구 버전 (이슈 #19)

브랜치 `feat/19-retention-consent`. 마이그레이션 `V10__retention_and_consent.sql`. ADR 0020.
- `campaigns.retention_days INTEGER NOT NULL DEFAULT 365`(1~3650). `leads.anonymized_at TIMESTAMPTZ NULL`, `leads.consent_text TEXT`, `leads.consent_sha256 CHAR(64)`. `ck_leads_contact`를 "익명화되지 않은 행만 연락처 필수"로 교체.
- 동의 증빙: 신청 시 그 폼의 동의 문구 원문과 sha256을 lead에 저장. 명단 상세에서 "동의 문구 보기".
- 파기: 매일 03:00 KST 스케줄러(`@Scheduled`, 설정으로 끄기 가능)와 관리자 수동 실행 API `POST /api/admin/retention/run`. `created_at < now - retention_days`인 lead를 익명화: 이름·연락처(평문·암호·해시) NULL, payload의 값은 키만 남기고 값 제거, `anonymized_at` 기록. 지표 숫자는 유지(행 삭제 없음). 감사 로그 `retention.anonymize`(건수).
- UI: 캠페인 생성·수정에 보존 기간(일), 명단에서 익명화된 행은 "파기됨" 표시.
- 테스트: 경계 시각(정확히 retention_days), 다른 캠페인 영향 없음, 멱등, 지표 불변, 동의 문구 저장, 로그에 PII 없음.
