## Task 65: 감사 액션 목록 OpenAPI 생성과 새 감사 행의 IP 검증 (이슈 #65)

브랜치 `test/65-audit-openapi-ip`.

- `AuditLogController`의 `action` 파라미터 설명(또는 스키마 enum)을 `AuditAction` 값에서 만든다. 손으로 적은 목록을 없앤다. springdoc 커스터마이저(`OpenApiCustomizer`) 또는 파라미터 스키마 `allowableValues`를 enum에서 채우는 방식 중 단순한 쪽. 테스트: enum 값 전부가 `/v3/api-docs`의 해당 파라미터에 나타나고, 목록에 enum 밖 값이 없다.
- 새 감사 행의 IP: 신뢰 프록시(테스트 설정의 루프백)를 거친 `X-Forwarded-For`로 `form.publish`, `template.version.upload`, `creator.archive`, `auth.logout`을 하나씩 일으키고 `audit_logs.ip`가 XFF의 클라이언트 주소인지 확인한다. 공개 포트 요청이 XFF로 IP를 바꾸지 못하는 기존 테스트와 겹치지 않게 한다.
- OpenAPI 재생성. WORKPLAN 4·5번 완료 표시.

## Task 66: 로그인 시도 제한 공유 저장소와 /refresh 제한 (이슈 #66)

브랜치 `feat/66-shared-login-throttle`.

- **공유 저장소**: 로그인 실패 기록을 PostgreSQL 테이블(V13, 예: `login_failures(key_hash, failed_at)` + `(key_hash, failed_at)` 인덱스)에 둔다. 키는 기존 세 종류((이메일, IP) 쌍, 이메일, IP)이며 이메일·IP 원문을 저장하지 않는다: `PiiHasher`(HMAC, LEAD_HMAC_KEY) 또는 별도 도메인 접두어를 붙인 HMAC로 해시한 값만 쓴다(설계 선택을 ADR에 기록). 한도·윈도·Retry-After 규칙(ADR 0021)은 그대로다.
  - 동시성: 같은 키로 동시에 실패가 들어와도 한도를 넘겨 통과시키지 않아야 한다. 시도 전에 자리를 잡고 성공·중단이면 돌려주는 현재 의미를 유지한다(트랜잭션과 `pg_advisory_xact_lock(hashtext(key))` 또는 행 잠금 중 택일, 이유를 ADR에).
  - 정리: 윈도가 지난 행을 지우는 정리(스케줄러, 기존 `SchedulingConfig` 사용)와 테스트. 성공 시 쌍 카운터 초기화 의미 유지.
  - 인메모리 `SlidingWindowLimiter`는 제출 rate limit 등 다른 곳에서 쓰면 남기고, 로그인에서는 DB 저장소로 바꾼다. 인메모리 LRU 밀어내기 한계(ADR 0021 2026-10-24 기록)가 해소됨을 변경 기록에 쓴다.
  - 테스트: 두 개의 throttle 인스턴스(같은 DB)가 카운터를 공유한다, 재시작(새 인스턴스) 뒤에도 잠금이 유지된다, 동시 실패에서 한도 초과 통과가 없다, 원문 이메일·IP가 테이블에 없다, 정리.
- **/refresh 제한**: `POST /api/admin/auth/refresh`에 IP별 rate limit(기본 분당 30, 설정값 `app.auth.refresh-rate-limit`, `.env.example` 필요 시). 넘으면 429 `too_many_requests` + Retry-After(기존 ProblemDetail 코드 재사용 여부 확인). 정상 회전(access 만료마다 1회)에 걸리지 않는 값인지 근거를 ADR에. 테스트: 한도 내 성공, 초과 429, 다른 IP는 별도.
- ADR 0021 변경 기록. GUIDE·TROUBLESHOOTING·WORKPLAN 3번 갱신. `DatabaseCleaner.truncateAll`에 새 테이블 추가.

## Task 67: 개인정보 키 교체 절차 (이슈 #67)

브랜치 `feat/67-pii-key-rotation`.

- **암호화 키(LEAD_ENC_KEY) 교체, 온라인**:
  - 새 암호문 형식 버전 2: `2 | keyId(1B) | iv(12B) | ciphertext+tag`, AAD는 `2:{keyId}:{column}` 같은 형식으로 키 id까지 묶는다. 버전 1(키 id 없음)은 키 id 1로 읽는다(기존 데이터 호환). 새로 쓰는 값은 항상 현재 키 id의 버전 2.
  - 설정: `LEAD_ENC_KEY`(현재 키), `LEAD_ENC_KEY_ID`(1~255, 기본 1), `LEAD_ENC_PREVIOUS_KEYS`(선택, `id:base64,id:base64`). 키 id 중복·현재 키와 같은 id의 이전 키·형식 오류는 기동 실패. 키 분리 검사(`SecretKeyMaterial`)에 이전 키도 포함.
  - 재암호화 배치: 현재 키 id가 아닌 암호문을 keyset으로 읽어 현재 키로 다시 쓴다. `pg_try_advisory_xact_lock`(파기와 다른 lock key), 배치 크기 설정, 수동 실행 `POST /api/admin/pii/reencrypt[?dryRun=true]`(감사 `pii.reencrypt` 필수 기록, 건수만), 진행 상황 응답(남은 건수). 익명화된 행(암호문 NULL)은 건너뛴다.
  - `pii_key_check`: 표식 행도 재암호화 대상이다. 기동 확인은 표식이 알려진 키(현재 또는 이전) 중 하나로 풀리면 통과하고, 어느 키로도 안 풀리면 지금처럼 기동 실패. 이전 키를 설정에서 지워도 되는지 판단하는 방법(남은 건수 0)을 API 응답과 GUIDE에.
- **HMAC 키(LEAD_HMAC_KEY) 교체, 기동 시 오프라인**:
  - 중복 판정 해시는 유니크 인덱스에 걸려 있어 키가 섞이면 중복을 놓친다. 그래서 온라인 이중 해시 대신, `LEAD_HMAC_PREVIOUS_KEY`가 설정된 채 기동하면 웹 서버가 요청을 받기 전에(`PiiKeyCheck`와 같은 시점, 그보다 먼저 또는 그 안에서) 모든 신청의 `phone_hash`·`email_hash`를 원문 복호화 → 새 키로 재계산해 배치로 바꾸고, 표식 행의 HMAC도 새 키로 바꾼다. 재시작 후 `LEAD_HMAC_PREVIOUS_KEY`를 지우면 끝. 같은 폼의 재계산 결과가 충돌하면(이론상 불가하지만) 중단하고 알린다. 중간에 실패해도 다시 기동하면 이어서 끝낼 수 있어야 한다(행마다 어느 키의 해시인지 판단할 방법: 표식 행 갱신을 마지막에, 그리고 이전 키 해시와 같은 행만 바꾸는 방식 등. ADR에).
  - 테스트: 이전 키로 만든 신청이 교체 뒤 같은 연락처 재신청에서 409, 표식 갱신, 중단 후 재기동 시 이어서 완료, 이전 키 없이 새 키만 주면 지금처럼 기동 실패.
- 마이그레이션은 필요하면 하나(V14). 형식 버전으로 해결되면 없음.
- ADR 0022 PII 키 교체. ADR 0015 변경 기록. GUIDE에 운영 절차(키 생성 → 설정 → 재기동 → 재암호화 → 남은 0 확인 → 이전 키 제거), TROUBLESHOOTING, `.env.example`, ROADMAP·WORKPLAN 1번 갱신. 관리자 화면은 필수가 아니다(API와 절차 문서로 충분, 넣는다면 흑백 토큰).
